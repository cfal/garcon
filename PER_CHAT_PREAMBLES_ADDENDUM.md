# Per-Chat Preambles Addendum

Status: execution-ready proposal

Audience: Garcon server, transcript, command, and web engineers

Governing design: `docs/transcript-ledger-v5-design.md`, revision 34

Extends: `PREAMBLES_DESIGN.md`

## Summary

The workspace preamble catalog remains the source of reusable preamble definitions and the master eligibility gate. Each chat additionally owns an explicit, independently ordered selection of catalog IDs in `chats.json`. An eligible preamble applies only when it is both selected by the chat and enabled and in scope in the current catalog.

New independent chats snapshot the current enabled, matching catalog IDs in catalog order. Forks and continuations copy the source chat's current selection. An in-place agent switch preserves it. Existing persisted chats that predate this addendum normalize to an empty selection.

Saving a changed selection on an existing chat persists the new selection first, appends a distinct title-only `Preambles updated` presentation notice, and arms the next ordinary input. Save never sends provider work, modifies an admitted prompt, steers, interrupts, cancels, or restarts an active run. The next ordinary input resolves the then-current catalog in the chat's saved order and produces the existing adjacent `Preambles applied` notice and receipt-backed private prefix.

This addendum deliberately chooses lean cross-store persistence. `chats.json` is authoritative. There is no recovery journal or prepared operation artifact for the subsequent ledger notice. A process failure after the registry commit and before the notice commit may leave a correctly updated selection without its `Preambles updated` row. The API never claims that this partial outcome rolled back.

Catalog IDs are canonical server-generated UUID v4 values. Deleted IDs move atomically into a bounded workspace tombstone set and can never be reused. A chat keeps deleted IDs in its ordered selection, reports them as unavailable, and skips them without failing application. The tombstone prevents a later catalog entry from silently acquiring the meaning of an old selection.

## Resolved Product Decisions

These decisions supersede only the catalog-wide resolution assumptions in the original preamble design. Its prefix, receipt, application notice, native sanitation, privacy, and provider-neutrality decisions remain unchanged.

- Catalog `enabled` is a workspace-wide master switch. A disabled preamble never applies even when a chat selects it.
- Catalog project scope remains authoritative. Selection does not override exact or nested path matching.
- A chat stores an ordered allowlist of preamble IDs. Application order is this list order, never current catalog order.
- Selected IDs remain stored when their catalog entries are disabled, outside the current project scope, or deleted.
- Missing catalog IDs are reported as `missing` and skipped gracefully at Save projection and input application.
- UUID v4 IDs are generated by the server and permanently retired on deletion. No deleted ID can later resolve to a different preamble.
- Catalog create, edit, enable, disable, delete, or reorder never mutates a chat selection and never arms existing chats.
- An untouched new-chat form uses server defaults at actual chat creation. An explicit empty list means no preambles.
- Existing persisted chats with no selection field normalize to revision zero and an empty list.
- A fork, including a historical-point fork, copies the source chat's current configuration rather than inferring configuration from the fork watermark.
- Continuation and self-handoff copy the source selection. The target starts at selection revision zero and then diverges independently.
- In-place agent switch preserves the chat selection and its revision.
- Scheduled new chats resolve ordinary new-chat defaults at actual creation. Scheduled input to an existing chat preserves its current selection.
- A delegated new chat uses ordinary new-chat defaults unless the operation is explicitly a continuation.
- A changed live selection applies on the next ordinary input. Steers, goal controls, server controls, permission decisions, and compaction controls neither apply nor consume it.
- An already admitted input retains its captured prefix. Queued inputs resolve selection at dequeue and admission, not queue insertion.
- Every changed Save appends one `Preambles updated` notice. Multiple Saves before the next ordinary input retain all update notices, but only the latest saved selection applies.
- An unchanged Save creates no revision, notice, invalidation, or reapplication.
- Reordering selected IDs is a change.
- Saving `[]` appends `Preambles updated: None enabled`; the next ordinary input consumes a zero-match boundary without an application notice or prefix.
- The update notice records entries eligible in one catalog snapshot captured for the Save. The later application notice records what actually applied.
- Catalog changes between Save and application may change eligibility, titles, content, and the actual applied set.
- Selection changes do not erase instructions already present in a provider's conversation.

Required UI copy:

> Applies with the next regular message. Current responses are unchanged.

## Goals

- Let users choose and order preambles independently for each chat.
- Support configuration before creation and reconfiguration at any later time.
- Preserve correct behavior across new chat, fork, continuation, scheduled creation, and in-place agent switch.
- Keep the catalog as the single body/scope authority and the chat registry as the selection authority.
- Skip deleted references safely without silently dropping user intent from the saved list.
- Make catalog identity non-reusable for the lifetime of the workspace.
- Preserve provider-neutral prefixing, receipt-backed sanitation, and body privacy.
- Keep Save independent of active provider execution while strictly ordering it before the next input admission.
- Provide typed, revisioned REST and WebSocket contracts and durable, idempotent notice insertion.
- Keep the browser architecture split between catalog management and chat-selection editing.

## Non-Goals

- Overriding catalog enablement or project scope from a chat.
- Automatically reapplying preambles after a catalog edit, path edit, or browser reconnect.
- Changing an active run, reissuing an admitted prompt, or removing instructions from provider-native context.
- Inferring current selection from historical `Preambles applied` or `Preambles updated` notices.
- Persisting preamble bodies, scopes, paths, or catalog snapshots in `chats.json` or the ledger.
- Recovering a missing update notice after a process crash without a new explicit client operation.
- Introducing a cross-store transaction journal, durable execution recovery, or a new public busy predicate.
- Teaching `server-agents/**` about selection, notices, boundaries, or prefixes.
- Making update-notice history survive manual native Reload with precise placement.

## Current System and Required Change

The implemented catalog lives in `common/preambles.ts` and `server/preambles/{store,service,matching,catalog-budget}.ts`. `PreambleService.resolve()` currently scans enabled, matching entries in catalog order. Catalog create uses `crypto.randomUUID()`, but shared normalization currently accepts any nonblank ID and deletion forgets the ID.

The chat registry in `server/chats/store.ts` is version 5 and currently stores only `pendingPreambleBoundary` for preamble behavior. `ALLOWED_PATCH_FIELDS`, the persisted-entry codec, `addChat()`, `updateChat()`, and `cloneRegistryEntry()` all enumerate nested ownership and must explicitly gain selection support.

Boundary producers are:

- `server/commands/start-commands.ts` for new chats;
- `server/chats/fork-chat.ts` for promptful and promptless forks;
- `server/commands/self-handoff-commands.ts` for continuation;
- `server/chats/agent-ownership-journal.ts` for in-place switches.

`server/agents/registry.ts` resolves the catalog at ordinary input admission. Its durable proof query and pending-field compare-and-clear currently identify a boundary by `(kind, ownershipEpoch)`. A repeatable live selection-change boundary additionally requires `selectionRevision`; otherwise the first application in an ownership epoch would suppress every later Save in that epoch.

`server/ledger/preamble-application.ts` and the existing receipt/sanitation path remain the application authority. The new update notice is not an application notice and must not enter `collectPreambleHistoryEvidence()`, which requires application notice/input adjacency.

The existing catalog dialog remains the only catalog editor. New-chat state currently has no selection field, and `CurrentChatMenuItems.svelte` currently has no selection action.

## Catalog Identity and Permanent Retirement

### Canonical ID contract

Add one shared identity guard and use it everywhere catalog or selection IDs cross a boundary:

```ts
export type PreambleId = string;

export function isPreambleId(value: unknown): value is PreambleId {
  return typeof value === 'string'
    && /^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$/u.test(value);
}
```

Only the canonical lowercase UUID v4 spelling is accepted. IDs are not trimmed or case-folded. `PreambleService.create()` calls `crypto.randomUUID()` once by default and validates the result before persistence. The injectable ID factory remains a test seam, but an invalid, active, or retired result is rejected rather than normalized or retried in a loop.

Update `normalizePreamble()`, catalog mutation requests, selection requests, notice-reference validation, and persisted-file parsing to use the same guard. Test fixtures use deterministic canonical UUID v4 strings.

### `preambles.json` version 2

The persisted catalog becomes:

```json
{
  "version": 2,
  "revision": 18,
  "preambles": [],
  "retiredPreambleIds": [
    "936903ad-8b98-43eb-a7d4-c17ce0dc18d8"
  ]
}
```

The active array remains ordered. `retiredPreambleIds` is an unordered logical set serialized in insertion order for stable files. Normalization requires:

- every active and retired ID is a canonical UUID v4;
- active IDs are unique;
- retired IDs are unique;
- active and retired sets are disjoint;
- no unknown file keys exist;
- all existing catalog invariants still hold.

Version 1 migrates at initialization before the service becomes available. Every active version-1 ID must already be a canonical UUID v4; invalid state fails visibly instead of being rewritten under a different ID. Migration writes version 2 with an empty retired set. Deleted preambles from before version 2 cannot be reconstructed, but per-chat selection did not yet exist and therefore cannot reference them. The permanent non-reuse guarantee begins with the version-2 migration.

Define:

```ts
export const PREAMBLE_ID_LIFETIME_MAX_COUNT = 100_000;
export const PREAMBLES_FILE_MAX_BYTES = 64 * 1024 * 1024;
```

The lifetime count is `active IDs + retired IDs`, not merely tombstones. Creation fails with `PREAMBLE_ID_LIFETIME_LIMIT_REACHED` before generating or writing an ID when the count is at the ceiling. Deletion moves one active ID to the retired set, so it does not increase the lifetime count and can always retire every admitted active entry. The store never prunes, compacts, reuses, or silently drops tombstones. A persisted or candidate file above either bound fails closed.

Creation checks collisions against both sets under the existing catalog mutation lock. A generated collision fails with `PREAMBLE_ID_COLLISION`; it is not silently regenerated because the collision may indicate a broken or injected generator. Deletion splices the active record and appends its ID to `retiredPreambleIds` in the same atomic catalog write and revision increment.

Catalog persistence uses the same commit-aware atomic-write result required for `chats.json`. A failure before rename changes neither the in-memory snapshot nor the authoritative file. If rename completed but final directory sync failed, the store installs the candidate snapshot in memory, returns a committed-but-durability-unknown outcome, and fences later catalog mutations until an explicit sync retry succeeds or restart reloads the file. `PreambleService` emits invalidation for that installed snapshot before surfacing `PREAMBLE_CATALOG_SAVE_UNKNOWN` to the caller. The store never restores the old snapshot or permits a later mutation to overwrite the renamed candidate. This is essential for deletion: a committed tombstone cannot be forgotten while the process continues. Reads remain available from the installed snapshot during the mutation fence.

The public catalog snapshot continues to return active preambles only. Tombstones are internal persistence state and are never sent to browsers, notices, shares, or exports.

## Per-Chat Selection Model

Add shared contracts in `common/preambles.ts`:

```ts
export interface ChatPreambleSelection {
  readonly revision: number;
  readonly orderedPreambleIds: readonly PreambleId[];
}

export type PreambleSelectionUnavailableReason =
  | 'missing'
  | 'disabled'
  | 'out-of-scope';

export interface PreambleSelectionReference {
  readonly id: PreambleId;
  readonly title: string;
}

export interface UnavailablePreambleSelectionReference {
  readonly id: PreambleId;
  readonly reason: PreambleSelectionUnavailableReason;
}

export interface PreambleSelectionProjection {
  readonly catalogRevision: number;
  readonly eligiblePreambles: readonly PreambleSelectionReference[];
  readonly unavailable: readonly UnavailablePreambleSelectionReference[];
}
```

Selection normalization requires:

- a nonnegative safe-integer revision;
- zero through `PREAMBLE_MAX_COUNT` IDs;
- canonical UUID v4 spelling;
- no duplicates;
- preserved order;
- no truncation, deduplication, sorting, or catalog lookup during persistence parsing.

Missing selection on a persisted chat normalizes to:

```ts
{ revision: 0, orderedPreambleIds: [] }
```

A present malformed selection rejects `chats.json`; corruption is not interpreted as deselection.

### `chats.json` ownership

Keep registry version 5 and add one additive field to every normalized entry:

```json
{
  "preambleSelection": {
    "revision": 3,
    "orderedPreambleIds": [
      "3502b645-222b-49d2-ac39-1c91f9fb1174",
      "80becfa6-c9c7-4b31-9190-fd23c0bedf9c"
    ]
  }
}
```

`ChatRegistryEntry` owns a required normalized `preambleSelection`. `NewChatRegistryEntry` also requires an already-resolved selection so creation callers cannot accidentally confuse persisted absence with creation defaults. Add it to `ALLOWED_PATCH_FIELDS`; normalize and clone its ID array on ingest, update, read, list, rollback snapshots, and persistence.

Selection revision increments exactly once for a changed existing-chat Save. New chat, fork, and continuation targets start at revision zero regardless of how many IDs their initial snapshot contains. Agent switch preserves revision. Revision exhaustion rejects further changes.

Bodies, title history, catalog copies, scope, paths, and eligibility are not registry fields.

### Resolution

Replace catalog filtering with an ordered lookup for selected chats:

```ts
export function resolvePreambleSelection(
  selection: ChatPreambleSelection,
  catalog: PreamblesSnapshot,
  canonicalProjectPath: string,
): {
  readonly eligible: readonly Preamble[];
  readonly unavailable: readonly UnavailablePreambleSelectionReference[];
} {
  const byId = new Map(catalog.preambles.map((preamble) => [preamble.id, preamble]));
  const eligible: Preamble[] = [];
  const unavailable: UnavailablePreambleSelectionReference[] = [];

  for (const id of selection.orderedPreambleIds) {
    const preamble = byId.get(id);
    if (!preamble) {
      unavailable.push({ id, reason: 'missing' });
    } else if (!preamble.enabled) {
      unavailable.push({ id, reason: 'disabled' });
    } else if (!preambleScopeMatches(preamble.scope, canonicalProjectPath)) {
      unavailable.push({ id, reason: 'out-of-scope' });
    } else {
      eligible.push(structuredClone(preamble));
    }
  }
  return { eligible, unavailable };
}
```

The implementation reuses the existing exact/nested scope matcher. It must iterate selection IDs and look up catalog records; filtering the catalog through a selection set would preserve the wrong order.

Missing IDs remain in `orderedPreambleIds` through reads, Saves, forks, continuations, and agent switches. They appear in `unavailable` and do not appear in either update or application title lists. Permanent tombstones ensure they can never become eligible again.

### Defaults and inheritance

| Situation | Initial selection |
| --- | --- |
| New independent interactive or CLI chat, selection omitted | Enabled, matching catalog IDs in catalog order, resolved from the canonical creation path at actual creation |
| New independent chat, explicit list | Exactly the supplied ordered list, including explicit `[]` |
| Existing persisted chat with no field | Empty, revision zero |
| Fork at any watermark | Source chat's current ordered IDs, target revision zero |
| Continuation or self-handoff | Source chat's current ordered IDs, target revision zero |
| In-place agent switch | Preserve ordered IDs and revision |
| Scheduled new chat | Resolve omitted defaults at actual creation |
| Scheduled existing-chat input | Preserve existing selection |
| Delegated new chat with parent relation only | Ordinary new-chat defaults |

Every creation path writes an explicit normalized selection. No persisted `inherit defaults` mode exists.

## Pending Boundary Identity

Extend the boundary union without changing existing lifecycle proof shapes:

```ts
export type PendingPreambleBoundary =
  | {
      readonly kind: 'new-chat' | 'fork' | 'continuation' | 'agent-switch';
      readonly ownershipEpoch: string;
    }
  | {
      readonly kind: 'selection-change';
      readonly ownershipEpoch: string;
      readonly selectionRevision: number;
    };
```

Add `selection-change` to the boundary kind contract. The normalizer permits `selectionRevision` only on that variant. Persisted selection-change boundaries must match both the current `agentOwnershipEpoch` and current `preambleSelection.revision`. Lifecycle boundaries retain their released shape and remain readable unchanged.

Add one shared equality helper and use it in every proof query and compare-and-clear:

```ts
export function samePreambleBoundary(
  left: PendingPreambleBoundary,
  right: PendingPreambleBoundary,
): boolean {
  return left.kind === right.kind
    && left.ownershipEpoch === right.ownershipEpoch
    && (left.kind !== 'selection-change'
      || (right.kind === 'selection-change'
        && left.selectionRevision === right.selectionRevision));
}
```

`server/ledger/preamble-application.ts`, ledger codecs, native evidence, Reload reconciliation, and `server/agents/registry.ts` use the complete identity. The current ownership-epoch-only clearing check is insufficient and must be removed.

When a changed selection is saved:

- if an unconsumed lifecycle boundary is pending, retain it; its first input resolves the newest selection;
- if the persisted pending boundary is already proven consumed in the current ledger, treat it as stale and do not retain it;
- otherwise install or replace a `selection-change` boundary for the new selection revision;
- never rotate `agentOwnershipEpoch` merely to reapply preambles.

An agent switch replaces an old selection-change boundary with the new `agent-switch` lifecycle boundary while preserving the current selection. Its first ordinary target-owner input applies that selection once.

## Existing-Chat Save Protocol

### Serialization and active execution

Create a focused `ChatPreambleSelectionService` modeled structurally on `ChatRowService`: it owns chat/view validation, revision checks, the shared `chat:${chatId}` mutation lock, ownership-transfer fencing, registry persistence, the update notice, and error translation. It never calls a provider configuration API.

Save remains allowed while a provider run owns execution. The service does not acquire a direct-turn reservation, compose a provider request, or add a public busy predicate. Output from the active run continues normally.

The Save and the next direct or queued ordinary-input admission must additionally share a narrow per-chat selection/admission lock:

- Save holds it from its final validation through the registry write and update-notice attempt.
- Direct admission holds it while it re-reads the registry selection, resolves the catalog, and commits the boundary input.
- Queue draining holds it around `dequeueNextTurn()` and its synchronous `registerQueued()` callback.
- Steers and control deliveries do not need it because they cannot consume the boundary.

This lock is internal coordination, not execution ownership or a public busy predicate. It prevents an input from observing the new selection before its update notice attempt. It also avoids making synchronous queued admission await inside the dequeue transition. Lock acquisition order is fixed and tested: the existing chat mutation lock precedes the selection/admission lock for Save; queue admission never acquires the chat mutation lock.

Reload, project-path changes, ownership transfers, fork/continuation capture, and deletion must use the shared chat mutation boundary and remain serialized with Save. Multi-chat operations retain their existing deterministic lock ordering while taking the source lock for selection capture. Pending ownership transfer rejects Save. The target chat ID and transcript view are captured from the invoked window before any `await` and never retargeted if browser focus changes.

### Lean authoritative-first sequence

For a request, under those locks:

1. Require the chat, current transcript view, ownership fence, and expected selection revision.
2. Check durable notice identity in the current view before the revision conflict check. An identical completed retry returns `duplicate`; changed content for the identity returns `IDEMPOTENCY_CONFLICT`.
3. Normalize IDs without requiring catalog membership. Missing UUIDs remain valid selection references.
4. After the expected revision succeeds, compare the normalized ordered list with the stored list. If unchanged, capture a catalog snapshot only to return the current projection and return `unchanged` without composition validation, writing, noticing, invalidating, or arming.
5. For a changed list, capture one catalog snapshot and resolve current eligibility in selection order.
6. Validate the exact currently eligible composition in selected order, including chat-ID expansion, combined length, and the reserved file-context separator.
7. Build the next selection revision and pending boundary, repairing any ledger-proven stale pending boundary as described above.
8. Durably write the selection and pending boundary together to `chats.json`. This is the authoritative decision.
9. Append one idempotent typed update notice to the selected transcript view.
10. Schedule `chat-preambles-invalidated` after the committed notice's `chat-messages` event on the per-chat server-event queue. If notice append fails, still schedule invalidation before returning the partial failure when possible.
11. Return success only when both the registry decision and update notice committed.

There is no compensating registry write after step 8. Restoring the old selection would make a committed `chats.json` decision disagree with the returned or possibly committed notice.

The shared atomic JSON writer must expose whether rename occurred, and both registry and catalog stores consume that phase-aware result. A pre-rename registry failure leaves in-memory state unchanged and returns an ordinary save failure. If rename completed but final directory sync failed, retain the new in-memory selection, report durability as unknown, and fence another selection Save until the registry is reloaded or a later explicit flush succeeds. Do not use `ChatRegistry.updateChat(..., { flush: true })` unchanged, because its generic conditional rollback treats every rejection as pre-commit even though `writeJsonFileAtomic()` may reject after rename.

### Accepted crash window

The following is intentional:

```text
chats.json selection + boundary commit
              |
              | process failure here
              v
ledger Preambles updated notice
```

After such a failure:

- the new selection remains authoritative;
- the next ordinary input still applies it once;
- the transcript may permanently lack that one `Preambles updated` notice;
- restart does not synthesize or backfill the notice;
- reconnect refreshes selection from the server;
- historical `Preambles applied` evidence remains exact and unaffected.

This is the user-approved lean posture. It is narrower than the governing ledger's application guarantee: the later application notice and its input still commit atomically. Only the configuration-change presentation row is lossy.

If registry persistence succeeds and ledger append fails without process death, return a typed partial error that says the selection was saved and the notice was not:

```json
{
  "success": false,
  "errorCode": "PREAMBLE_SELECTION_NOTICE_FAILED",
  "message": "The selection was saved, but its transcript notice could not be recorded.",
  "retryable": false,
  "selectionCommitted": true,
  "selection": {
    "revision": 4,
    "orderedPreambleIds": []
  }
}
```

The browser adopts the returned selection as its new base, keeps the dialog available, and shows the warning. It does not claim rollback or fabricate a notice. A registry write whose commit is unknown returns `PREAMBLE_SELECTION_SAVE_UNKNOWN` with `selectionCommitted: 'unknown'` and requires a refresh before another edit.

## Idempotent Update Notice

Add a distinct public notice detail:

```ts
export interface PreambleSelectionChangedNoticeDetail {
  readonly type: 'preamble-selection-changed';
  readonly preambles: readonly PreambleSelectionReference[];
}
```

Unlike `preamble-application`, the list permits zero entries. The fixed message is `Preambles updated`. Empty presentation renders `None enabled`. References are eligible `{id,title}` snapshots from the Save's captured catalog revision. Disabled, out-of-scope, and missing selections are not listed.

Do not reuse `preamble-application`. The native-history evidence collector requires each application notice to be adjacent to a receipt-bearing input; a standalone update notice under that discriminant would make Reload and native-fork sanitation fail closed.

The ledger stores a private notice detail carrying only the durable submission identity needed for retry:

```ts
export interface LedgerPreambleSelectionChangedNoticeDetail extends JsonObject {
  readonly type: 'preamble-selection-change';
  readonly clientMessageId: string;
  readonly requestFingerprint: string;
  readonly selectionRevision: number;
  readonly preambles: readonly PreambleSelectionReference[];
}
```

The fingerprint covers the canonical request identity and ordered selected IDs, including the expected selection revision, but excludes catalog titles, bodies, paths, and catalog revision so a retry survives catalog edits. Presentation converts the private type to the exact public `preamble-selection-changed` detail. Share and export see only public references.

Extend the ledger submission-index codec to allow `client_message_id` on this private notice type as well as CLI rows. The append checks the current view's submission index before mutation. Same identity and fingerprint returns the original row and selection revision without a second broadcast. Same identity with a different fingerprint, a user-input collision, or a CLI-row collision throws `IDEMPOTENCY_CONFLICT`.

A completed duplicate check precedes expected selection revision validation, but only after the request's transcript view is proven current. A retry against a replaced view receives `STALE_TRANSCRIPT_VIEW` and can never deduplicate into another view.

Manual Reload intentionally drops update notices from the imported current binding because provider-native history has no position for this Garcon-only configuration event. The selection itself remains in `chats.json`. Frozen projection does not preserve update notices. Fork and continuation configuration is copied from registry state rather than inferred from notice history.

## REST Contracts

### Existing-chat projection

Add:

```text
GET /api/v1/chats/preambles?chatId=<chatId>
```

Response:

```ts
export interface ChatPreambleSelectionTargetResponse {
  readonly success: true;
  readonly chatId: string;
  readonly transcriptViewId: string;
  readonly selection: ChatPreambleSelection;
  readonly projection: PreambleSelectionProjection;

```

The route ensures/adopts the current transcript view, captures the chat's canonical project path, and projects one current catalog snapshot. It returns no body, scope, path, or tombstone data. An unavailable missing ID returns only its ID and `reason: 'missing'`.

### Existing-chat mutation

Add:

```text
PUT /api/v1/chats/preambles
```

Request:

```ts
export interface UpdateChatPreambleSelectionRequest {
  readonly chatId: string;
  readonly transcriptViewId: string;
  readonly clientRequestId: string;
  readonly clientMessageId: string;
  readonly expectedRevision: number;
  readonly orderedPreambleIds: readonly PreambleId[];
}
```

The JSON request body is limited to 32 KiB before parsing. The normal selection limit remains 100 IDs.

Success:

```ts
export interface UpdateChatPreambleSelectionResponse {
  readonly success: true;
  readonly commandType: 'chat-preambles-update';
  readonly clientRequestId: string;
  readonly clientMessageId: string;
  readonly chatId: string;
  readonly transcriptViewId: string;
  readonly status: 'updated' | 'unchanged' | 'duplicate';
  readonly mutationRevision: number;
  readonly noticeOrdinal: number | null;
  readonly selection: ChatPreambleSelection;
  readonly projection: PreambleSelectionProjection;
}
```

`mutationRevision` is the revision created by the original operation. For `unchanged` it is the current revision. For a duplicate followed by later edits, `selection` is the current chat selection while `mutationRevision` and `noticeOrdinal` identify the original operation.

Errors include:

- request validation or size failure (`400`/`413`);
- `SESSION_NOT_FOUND` (`404`);
- `STALE_TRANSCRIPT_VIEW` (`409`);
- `PREAMBLE_SELECTION_REVISION_CONFLICT` (`409`, refreshable);
- `IDEMPOTENCY_CONFLICT` (`409`);
- pending ownership transfer (`409`, retryable);
- `PREAMBLE_SELECTION_COMPOSITION_INVALID` (`422`);
- `TRANSCRIPT_UNAVAILABLE` (`422`);
- `PREAMBLE_SELECTION_NOTICE_FAILED` (`503`, selection committed);
- `PREAMBLE_SELECTION_SAVE_UNKNOWN` (`503`, commit unknown).

### New-chat selection preview

Add a body-qualified, authenticated endpoint for the pre-chat form:

```text
POST /api/v1/preambles/selection-preview
```

Request is:

```ts
{
  readonly projectPath: string;
  readonly orderedPreambleIds?: readonly PreambleId[];
}
```

The server canonicalizes the path through the same project-path authority used by chat creation. Omitted IDs request current defaults; present IDs request a projection of that exact draft, including explicit empty and missing references. The response is:

```ts
{
  success: true;
  canonicalProjectPath: string;
  orderedPreambleIds: readonly PreambleId[];
  projection: PreambleSelectionProjection;
}
```

For omitted IDs, `orderedPreambleIds` contains enabled, matching entries in catalog order. For explicit IDs, order and missing references are preserved. The response contains no bodies. The new-chat picker separately loads the existing catalog store on user intent when it needs editable candidates. This preview is side-effect-free and does not guarantee later creation state; actual chat creation resolves omitted defaults again and validates an explicit selected composition before persistence.

`StartChatCommandRequest`, `ChatStartInput`, `NormalizedChatStart`, `NewChatConfig`, browser draft startup state, scheduled creation normalization, and start-command idempotency payloads gain:

```ts
readonly orderedPreambleIds?: readonly PreambleId[];
```

Omitted in a creation request means resolve current defaults on the server after project-path canonicalization. Explicit `[]` means none. The normalized start carries both the request intent (`defaults` or explicit IDs) and the resolved list used for `addChat()`. `startPayload()` and `startReplayPayload()` fingerprint only the canonical request intent, so a catalog change does not turn an identical retry into an idempotency conflict. The command record does not need the resolved default list: if preparation committed a chat, its selection is already in `chats.json`; if preparation did not commit a chat, a permitted pre-schedule retry resolves defaults at the later actual creation time. A duplicate of a completed start replays its original chat and never resolves newer defaults.

## WebSocket Contract

Add a body-free event:

```ts
export class ChatPreamblesInvalidatedMessage {
  readonly type = 'chat-preambles-invalidated' as const;

  constructor(
    public readonly chatId: string,
    public readonly revision: number,
  ) {}
}
```

Update the shared sender, parser, receiver, and contract tests together. This event is distinct from workspace `preambles-invalidated`, which continues to describe catalog mutations.

For a successful Save, schedule the event after the update notice's committed-row event through `server-event-wiring`'s per-chat task queue. For a notice-failed partial outcome, send the invalidation without a preceding row. A process crash may lose the event; reconnect refreshes an already-loaded current selection.

Clients accept only nondecreasing selection revisions. An open clean editor refreshes. An open dirty editor preserves its draft and shows a conflict. The event does not fabricate a transcript notice.

Catalog invalidation refreshes the catalog and reprojects an open selection editor without changing its saved IDs. A deleted selected ID therefore changes from a titled candidate to a stable `missing` row while staying in its selected position.

## Application and Composition

At an unconsumed boundary, `server/agents/registry.ts` reads the chat's current `preambleSelection`, captures one catalog snapshot, and calls `resolvePreambleSelection()`. It passes only the returned eligible entries to the existing ledger application composer.

Deleted, disabled, and out-of-scope entries contribute no prefix content, no application title, and no slash-command block. If all selected entries are unavailable, the ordinary input consumes the boundary with its private proof and creates no application notice or prefix.

Application order is the selected-ID order. Catalog reorder has no effect on any existing selection. Catalog rename/content/scope/enablement changes affect the later resolution of an already-selected active ID.

The exact eligible composition must be validated at each point that can introduce or consume a changed order:

- at explicit new-chat selection preparation and existing-chat changed Save, for early actionable feedback against the captured catalog snapshot;
- immediately before input commit, because catalog or project eligibility may have changed.

Validation uses selected order, target chat-ID expansion, exact prefix framing, combined length, and the reserved file-context separator. The current catalog-wide validator checks catalog order and does not prove every chat permutation safe. For example, individually valid entries can reconstruct the reserved separator only after chat-level reordering. A changed Save or explicit creation request rejects with `PREAMBLE_SELECTION_COMPOSITION_INVALID` before persistence. Admission can still encounter the same typed error after a later catalog or project change; it fails before storing anything and retains the pending boundary.

Treat `PREAMBLE_SELECTION_COMPOSITION_INVALID` and `PREAMBLE_SLASH_COMMAND_BLOCKED` as the two recoverable preamble admission errors through one shared predicate. `AcceptedInputHandler` retains a prepared new-chat, fork, or continuation target for either error instead of compensating it, allowing the user to reconfigure and retry. `QueueDrainer` consumes the offending queued entry, publishes the ordinary actionable turn-failure notice, preserves the boundary, and continues draining later entries for either error. Every other admission error retains its existing compensation and drain behavior.

The composition error message is actionable and body-free: `Selected preambles can’t be applied in this order. Reconfigure this chat’s preambles and try again.`

The provider slash-command rule uses the eligible selected set. A slash command is blocked only when at least one selected entry is currently eligible. Missing selected IDs are never an error and never block slash commands by themselves.

Same-`clientMessageId` input retries continue to return the original committed input and captured prefix consequence. They do not resolve a newer selection or catalog snapshot and do not redispatch.

## Transcript, Privacy, Reload, and Fork Semantics

Two separate durable facts exist:

| Fact | Detail | Meaning |
| --- | --- | --- |
| Configuration changed | `preamble-selection-changed` | Entries eligible in the Save's catalog snapshot |
| Prefix applied | `preamble-application` | Entries actually composed into one accepted provider prompt |

Both render immutable title snapshots. Neither contains bodies, scopes, paths, catalog revisions, or tombstone data. Only the application input carries its private prefix receipt and boundary proof.

The update notice follows ordinary presentation-only notice folds:

| Surface | Update notice | Body |
| --- | --- | --- |
| Live transcript, replay, background cache | yes | no |
| Search and preview | no | no |
| Resend, model context, carryover | no | no |
| Share snapshot | yes | no |
| Ordinary export | yes | no |
| Frozen projection | no | no |
| Manual native Reload of current binding | dropped | no |

The application notice retains all behavior from the governing design: adjacent atomic commit with its input, receipt-backed native sanitation, frozen-projection preservation, native-fidelity reconstruction, and title-only sharing/export.

Do not collect update notices as preamble history evidence. Do not infer selection from application/update notices after Reload, fork, continuation, restart, or catalog deletion. Registry configuration is authoritative.

Fork configuration copies the source registry selection current at fork preparation, even for a historical watermark. The fork's transcript seed follows existing frozen/native rules independently. Continuation does the same at its target preparation. Both target lists are cloned and start at revision zero. A later edit to either source or target cannot alias the other.

Preamble bodies remain absent from ledger rows, selection state, notices, API projections, WebSocket events, browser caches for selection metadata, search, preview, resend, carryover, shares, and ordinary exports. Existing receipt sanitation remains the only native-history body-removal authority. Logging may include chat ID, revisions, IDs, eligibility reasons, and error codes, but never content, composed prompts, or native excerpts.

## Failure Semantics

| Window or condition | Outcome |
| --- | --- |
| New catalog ID is malformed, active, or retired | Creation rejects; no retry loop or write |
| Catalog lifetime-ID or file-size ceiling reached | Creation rejects; no tombstone is pruned and no ID reused |
| Catalog deletion succeeds | Active row removed and UUID retired in one catalog write |
| Catalog write fails before rename | Old catalog snapshot remains authoritative; no invalidation |
| Catalog rename succeeds but directory sync is unknown | Candidate catalog/tombstone snapshot remains installed; mutations fence and clients receive invalidation |
| Selected ID was deleted | ID stays selected, projects as `missing`, and is skipped at application |
| Selected ID is disabled or out of scope | ID stays selected with its reason and is skipped |
| Catalog later creates another preamble | Its UUID cannot equal any retired selected ID |
| Selection request contains duplicate or non-UUID IDs | Validation failure; no normalization or partial Save |
| Expected selection revision is stale | Conflict with current selection/projection; no notice or boundary change |
| Ordered list is unchanged | `unchanged`; no revision, notice, invalidation, or boundary change |
| Changed selected order is unsafe at Save or explicit creation preparation | Request rejects before selection persistence |
| Identical list is saved after a catalog edit made it unsafe | `unchanged`; no validation or mutation; any already-pending boundary remains pending |
| Catalog or project change makes composition unsafe before application | Typed input rejection before ledger commit; boundary remains armed |
| Prepared new-chat/fork/continuation input hits unsafe composition | Prepared target is retained for reconfiguration and retry |
| Queued input hits unsafe composition | Entry is consumed with an actionable turn failure; boundary remains armed and later entries continue draining |
| Save while a provider run is active | Selection and notice commit; current run is untouched; next ordinary input applies |
| Ordinary input races Save | Selection/admission lock gives a total order; input is wholly before Save or after its notice attempt |
| Queued input reaches the head during Save | Dequeue waits outside its synchronous callback; the entry is neither lost nor paused permanently |
| Registry failure before atomic rename | Old selection remains authoritative; no notice |
| Registry rename succeeds but durability is unknown | New in-memory state retained, typed unknown result, further Saves fenced until reconciliation |
| Crash after registry commit, before notice | Selection and boundary survive; update notice may be absent permanently |
| Ledger notice append fails after registry commit | Typed `selectionCommitted: true` partial failure; never claim rollback |
| Invalidation is lost with process crash | Reconnect refreshes loaded selection; no synthetic notice |
| Multiple Saves precede input | Each successful change has an update notice; latest selection-change boundary replaces the older one |
| Save occurs with unconsumed lifecycle boundary | Lifecycle boundary retained and resolves latest selection |
| Stale persisted boundary already has ledger proof | Save does not retain it; new changed selection gets a selection-change boundary |
| Steer/control follows Save | Does not consume selection-change boundary |
| Next ordinary input has zero eligible entries | Stores boundary proof, no application notice/prefix |
| Duplicate completed Save request | Original update notice returned, no second write or broadcast |
| Same notice identity with changed request | `IDEMPOTENCY_CONFLICT` |
| Manual Reload | Selection remains; Garcon-only update notices in replaced current binding may be lost |
| Fork/continuation after update notice loss | Current registry selection still copies correctly |

## Migration, Rollout, and Rollback

### Migration

- Migrate `preambles.json` version 1 to version 2 with an empty retired-ID set after validating canonical active UUID v4 IDs.
- Keep `chats.json` at version 5. Missing `preambleSelection` becomes revision-zero empty selection.
- Existing pending lifecycle boundaries remain readable. If their old chat lacks selection, their first input consumes with zero matches.
- Existing ledger rows and version-one prefix receipts remain readable unchanged.
- The new update notice uses the existing `notice` row kind, so no SQLite schema or `PRAGMA user_version` change is required.
- The ledger codec gains a new private notice identity shape under the existing `client_message_id` index.
- Server and browser contracts deploy together; no dual API period is required.

### Rollout order

- Land UUID/tombstone migration and selection contracts before accepting selections.
- Land registry selection normalization/cloning and inheritance before changing admission resolution.
- Land complete boundary identity and selected-order validation before arming `selection-change`.
- Land private/public update-notice parsing and idempotency before exposing Save.
- Land REST/WS and browser controller before the menu/new-chat affordances.
- Enable the UI only with server, Lightpanda, and Chromium coverage in the same change.

### Rollback

A safe rollback stops accepting new selection changes and new selection-change boundaries while retaining:

- `preambles.json` version-2 parsing and retired IDs;
- `chats.json` selection and boundary parsing;
- update/application notice parsing and rendering;
- existing receipt/native sanitation logic.

Never downgrade the catalog to a representation that loses tombstones, reuse retired IDs, or remove receipt sanitation while native histories may contain framed prefixes.

## Alternatives Rejected

### Treat catalog `enabled` as only a default

Rejected because it would let a chat apply a workspace-disabled instruction and invalidate existing catalog budget and safety expectations.

### Remove unavailable IDs from chat selections

Rejected because a temporary disable/scope mismatch is not deselection, and silent cleanup destroys the user's ordering intent. Deleted IDs are cheap bounded references and permanent tombstones make them safe.

### Reuse deleted IDs after proving no current chat selects them

Rejected because notices and external stale clients may still carry the identity, scanning every durable surface is brittle, and UUID plus bounded tombstones makes reuse unnecessary.

### Store full preamble definitions per chat

Rejected because bodies and paths would be duplicated into enumeration state, catalog edits would have ambiguous propagation, and privacy/storage boundaries would weaken.

### Resolve selected entries by filtering catalog order

Rejected because it ignores the chat's explicit order.

### Apply immediately when Save occurs

Rejected because it would steer, restart, or synthesize provider work during an active run and would not correspond to a user-authored ordinary input.

### Append the update notice before registry persistence

Rejected because the transcript could announce a selection that never became authoritative.

### Compensate selection after notice failure

Rejected because registry atomic-write outcome can be ambiguous and compensation can overwrite a committed selection or race later changes.

### Add a recovery journal

Rejected for this lean version. It would close the selection-without-notice crash window but introduces preparation, recovery, cleanup, power-ordering, and admission-fence machinery disproportionate to a presentation-only notice. Reconsider only if exact configuration history becomes a product invariant.

### Reuse `preamble-application` for Save

Rejected because application evidence requires an adjacent receipt-bearing input and participates in native sanitation. Update is a different fact.

### Preserve update notices through native Reload

Rejected because provider-native history has no authoritative position for Garcon-only configuration changes. Configuration survives in `chats.json`; application history remains receipt-backed.

## Acceptance Criteria

- Every chat has a normalized, revisioned, independently ordered preamble selection.
- New-chat defaults, explicit none, fork/continuation copying, scheduled creation, and agent-switch preservation follow the matrix above.
- Existing chats with no field remain empty and are not retroactively populated.
- Deleted preambles remain selected as `missing`, never fail application, and can never be resurrected under the same ID.
- All active and retired catalog IDs are canonical UUID v4 values; deletion permanently retires IDs under explicit lifetime/file bounds.
- Catalog enabled/scope constraints and chat order jointly determine the eligible application set.
- Live Save is allowed during a run, changes no current provider work, and applies only at the next ordinary input.
- Direct and queued admission cannot overtake the Save's update-notice attempt.
- Selection-change proof identity includes revision, enabling repeated Saves in one ownership epoch.
- `Preambles updated` and `Preambles applied` are distinct typed, title-only facts with correct read folds.
- Registry-first/notice-second failure is reported accurately, and the accepted missing-notice crash window is documented and tested.
- Selected-order separator and size safety are validated at Save and again at application.
- Bodies remain absent from all Garcon presentation and conversational surfaces.
- REST and WebSocket contracts are typed and tested on sender and receiver paths.
- New-chat and window-menu selectors target the intended chat through rapid switches and multi-window use.
- Browser coverage proves loading, focus, responsive layout, background cache delivery, composer stability, and privacy.
