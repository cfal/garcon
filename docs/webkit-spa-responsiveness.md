# What makes Garcon feel slow across browsers?

For the subsequent fixes, paired production-build results and remaining bottlenecks, see the [optimization follow-up](webkit-spa-optimization-results.md).

**We know a cause of switching, a cause of opening popups, and which code path is expensive during scrolling. They are not the same problem.** Warm single-line typing did not get progressively worse from one to twelve quiet panes. At twelve panes it mattered *which chats were receiving output*: in one WebKitGTK comparison, the foreground key-to-frame median was 49 ms quiet, 51 ms with other non-tiled chats receiving turns, and 159 ms when the receiving chats were tiled. A separate test found a full sidebar projection can consume a frame in *either* engine. No measurements here establish iPhone latency or a general JavaScriptCore vs V8 speed ratio.

The useful question is: **how much work does one local interaction make the rest of the app do?** A small editor can replace a document stylesheet, a virtual list can synchronously measure newly mounted rows, and changing one chat preview can rebuild an index of every chat. Counting only visible DOM nodes, timing only event handlers, or measuring page load misses all three.

## Switching already-visible chats

Twelve tiled chats, no active turns, empty drafts. Click the transcript in another pane, versus the transcript in the already-current pane. Measure from trusted pointerdown to the second animation-frame callback after click. Check that the destination became current, the shared composer bound to its surface, its editor was ready, and all twelve original feed viewport elements stayed connected. Median ms, 12 warm samples per cell across counterbalanced Source/Formatted blocks:

| 12 panes | GTK Source: switch / same | GTK Formatted: switch / same | Chromium Source: switch / same | Chromium Formatted: switch / same |
| --- | ---: | ---: | ---: | ---: |
| Before the editor fix | 124 / 31 | **801 / 31** | 41 / 25 | 51 / 21 |
| Production build with static editor CSS | 191 / 43 | **212 / 44** | 48 / 21 | 58 / 22 |

Compare modes **within a build**. VM load changed across builds; this isn't evidence for a Source regression or a Chromium speedup. There is still appreciable switch work on both engines, especially GTK. The default mode is Formatted. On the older build, **Settings > Behavior > Message format > Source** is a useful diagnostic or workaround for switching, not for scrolling.

**The causal test:** keep Formatted mode, let Garcon destroy and recreate the editor as usual, and change only whether Tiptap's existing core stylesheet stays in the document on teardown. Alternate variants in the *same loaded page*. In the block observing head changes only (eight warm switches per variant), GTK's twelve-pane switches fell from **861 to 165 ms** (81%); in Chromium, **58 to 48 ms**. Head observation recorded one stylesheet removal and one insertion on every default switch, none when kept. The editable node was replaced in **both** variants. In a separate instrumented GTK block, the default switch took 833 ms; the editor's first option setup through mount took 9 ms and its destroy method 1 ms (medians). Timing the constructor alone would have missed the consequence of the changes it made to the page.

The [keyed editor](../web/src/lib/components/chat/composer/ComposerInputSurface.svelte) resets draft-specific editor state. [Tiptap 3.32.0](https://github.com/ueberdosis/tiptap/blob/388e722df0b36f5ac7d63cbd8b2354d43794360d/packages/core/src/Editor.ts#L202-L233) removes the sheet on last-editor unmount; [mount injects its rules](https://github.com/ueberdosis/tiptap/blob/388e722df0b36f5ac7d63cbd8b2354d43794360d/packages/core/src/Editor.ts#L632-L646). Garcon now [bundles the same rules with the composer](../web/src/lib/components/chat/composer/ComposerMarkdownEditor.svelte) and sets `injectCSS: false`. The fix doesn't keep an editor per pane, share undo history, intercept DOM methods, or turn formatting off. The actual fixed build had zero injected Tiptap sheets and retained the editor's computed ligature setting. [Switch samples](qa/webkit-spa-responsiveness/pane-switching.csv) include the diagnostic and both production builds.

**Residual cost:** [pointerdown changes focus ownership; click adopts the composer anchor](../web/src/lib/workspace/workspace-presentation-controller.svelte.ts). In a separate Source-only control, switching vs re-clicking took 130 vs 41 ms with two panes and 187 vs 49 ms with twelve in GTK (Chromium: 121 vs 22, 122 vs 27). On instrumented twelve-pane switches, GTK recorded a median ~90 DOM mutations, 53 in shared UI, with none in the other ten panes. This rules against every feed remounting, not against broader style recalculation. Track the old and new feed insets, shared composer placement, and current-pane chrome separately before changing focus semantics. [Source controls](qa/webkit-spa-responsiveness/source-click-control.csv).

## Typing and scrolling

**Typing.** With a short draft, focus and caret held fixed, real keydown to the second frame after input:

| Editor and fixture | GTK, 1 / 12 panes | Chromium, 1 / 12 panes |
| --- | ---: | ---: |
| Source, short chats | 57 / 55 ms | 26 / 18 ms |
| Formatted, 98 entries in the active chat | 27 / 31 ms | 22 / 24 ms |

These are separate fixtures, not an A/B of the two editors. Nine warm samples per cell. In 12-pane Source mode GTK saw the input event after 4 ms, versus 55 ms at the frame checkpoint. Those measurements start *inside* the page, so they exclude queued OS/browser input before the handler. The [textarea autosizer](../web/src/lib/components/ui/textarea/content-sized-textarea.svelte.ts) does alternate writes and geometry reads. Bypassing its fit for the measured one-line key, while verifying the same text, selection, focus and height, gave **62 ms instead of 55** in GTK. Not a supported fix. Don't debounce text input. Test line wraps, long formatted drafts, completion, IME and simultaneous incoming output independently. [Key samples](qa/webkit-spa-responsiveness/typing.csv).

**What a formatted key does.** In a separate Inspector capture of ten trusted keys, the [ProseMirror DOM observer](https://unpkg.com/prosemirror-view@1.42.6/src/domobserver.ts) that reconciles native edits accounted for 63 of 105 ms of recorded function self time at twelve panes, versus 68 of 118 ms at one pane. Its callback flushes editor and application work together; this isn't 63 ms of observer overhead, nor 63 ms per key. The [composer update handler](../web/src/lib/components/chat/composer/ComposerMarkdownEditor.svelte) assembles the Markdown source and walks the document for the node limit. A fixed-height, twelve-pane test with **24 vs 192 formatted paragraphs** (1,044 vs 8,528 source characters) gave 41 vs 55 ms to two frames in GTK, 23 vs 23 ms in Chromium. GTK's two short-draft blocks themselves had medians of 32 and 65 ms: insufficient evidence to blame draft length in this range. The test restored drafts through normal storage, verified the typed character and caret each time, and verified the saved Markdown after every block. [Draft-size samples](qa/webkit-spa-responsiveness/draft-size.csv).

**Typing while other panes update.** Same loaded page, twelve visible panes, same focused Formatted editor. Insert one character into a four-character draft, verify the result and caret, then remove the character with Backspace outside the sample. Alternate quiet blocks with blocks completing one short synthetic provider turn every 300 ms, alternating between two other visible chats. Both clients received about 3.3 completed turns/s in the active blocks. The quiet blocks observed zero DOM changes in those two feeds.

| 12 panes, quiet / active background | Keydown to input, median | Keydown to two frames, median | Keydown to two frames, p95 |
| --- | ---: | ---: | ---: |
| WebKitGTK | 4 / 4 ms | **34 / 67 ms** | **58 / 208 ms** |
| Chromium | 0.8 / 0.8 ms | 26 / 27 ms | 29 / 63 ms |

28 warm keys per condition per engine, ABBA block order (opposite orders between engines); p95 is the second slowest sample, not a population estimate. Other chats can delay foreground feedback **without mutating the foreground draft**. This challenge changes transcript delivery, row rendering, sidebar activity and server load together; it doesn't isolate which one to optimize. A series of completed turns is not token streaming. [Per-key timings and concurrent background mutations](qa/webkit-spa-responsiveness/typing-background.csv).

**Does it matter whether the recipients are tiled?** In a second run, keep the same twelve panes mounted, the focused draft and tile sizes fixed, and fourteen chats in the sidebar. Send the same approximately 3.3 completed turns/s to either two visible background chats or two non-tiled chats. Check that the recipients have two vs zero visible conversation panels, and count DOM records in the same two tiled feeds and the sidebar throughout. The sidebar updated in both active conditions; the two observed feeds recorded **zero** mutations during non-tiled delivery.

| 12 panes, 14 chats; key to two frames | Quiet median / p95 | Non-tiled recipients median / p95 | Tiled recipients median / p95 |
| --- | ---: | ---: | ---: |
| WebKitGTK | 49 / 66 ms | 51 / 108 ms | **159 / 275 ms** |
| Chromium | 23 / 28 ms | 22 / 38 ms | 22 / 31 ms |

28 warm keys per cell, two blocks per condition. In GTK the corresponding keydown-to-input medians were 4, 4 and 5 ms. The effect replicated for visible background work, but the magnitude changed between runs. Compare within each table. This discriminates *which path to trace*: maintaining and displaying another live conversation costs much more here than updating its catalog entry alone. It does not separate subscription, transcript state, row mounting and paint, or establish that a catalog with thousands of chats is cheap. [Recipient visibility samples](qa/webkit-spa-responsiveness/typing-recipient-visibility.csv).

**Continuous scroll is different.** Same 98-entry chat, 14 trusted wheel notches totaling 1,680 CSS pixels over about 780 ms. Confirmed delivered deltas, actual movement and different mounted row IDs. No active turn. Median browser-thread animation-frame callback interval during the train:

| Visible chat panes | GTK idle / scrolling | Chromium idle / scrolling | GTK scrolling p95 | Chromium scrolling p95 |
| --- | ---: | ---: | ---: | ---: |
| 1 | 16 / **119 ms** | 17 / 16 ms | 178 ms | 30 ms |
| 12 | 16 / **56 ms** | 17 / 17 ms | 107 ms | 27 ms |

Pooled intervals fully inside five warm wheel trains, not physical display FPS. A compositor may scroll while JS is starved; delayed virtual rows can still leave visible gaps. The single large tile was **worse** here, not better: its 806 px feed exposed many more rows than the small 86 px feed. Median 20 vs 10 new row IDs between endpoints. Pane count alone is a poor proxy for this workload.

A second, interleaved GTK control placed a simple native overflow scroller with 98 static paragraphs over the same viewport in the otherwise live workspace. At twelve panes the median callback gap was **24 ms in static text vs 147 ms in the live feed**; at one pane, **74 vs 189 ms**. Load varied considerably across runs; compare within a block. This control changes row contents, observers, scrollbar and virtualization together. It separates cheap content from the Garcon feed, not one specific subsystem. [Wheel and idle samples](qa/webkit-spa-responsiveness/scrolling.csv).

**Actual WebKit Inspector trace, not just geometry call counts.** Separate run on the fixed build, GTK MiniBrowser, 12 trusted X11 wheel notches in each direction. The twelve-pane downward gesture actually moved 1,164 px. The trace reported 266 ms of `FunctionCall` self time, including **180 ms attributed to the virtual-list scroll callback**, plus 214 ms in style recalculation, 39 ms layout and 28 ms paint. On the reverse gesture: 101 ms in that callback, 85 ms style, 8 ms layout, 14 ms paint. At one pane the same callback accounted for 246 ms down and 163 ms up. These are per-capture main-thread durations, not additive end-to-end latency or GPU times.

The callback maps to [VirtualListDomDriver](../web/src/lib/virt/virtual-list-dom-driver.ts) and [scrolled / publish](../web/src/lib/virt/virtual-list-transaction.ts). In the twelve-pane downward trace, styles were resolved inside the initial row-size `offsetHeight` fallback (~40 ms total), Svelte element-size bindings (~41 ms) and the [custom scrollbar's](../web/src/lib/components/chat/transcript/ConversationFeed.svelte) scroll-position reads (~32 ms); more style work ran outside those reads. A read can pay for earlier invalidation, so deleting the read is not automatically a win. [Trace summaries](qa/webkit-spa-responsiveness/webkitgtk-timelines.csv) and [call-site totals](qa/webkit-spa-responsiveness/webkitgtk-callsites.csv).

**Next scroll experiment:** the driver already uses ResizeObserver border-box sizes when available. Compare its synchronous first-mount fallback with waiting for the first observer delivery, and separately compare the custom thumb with a native scrollbar at the same content width. Hold viewport, content, overscan and gesture fixed; compare row mounting, layout and frame gaps. Reject any change that buys time with blank rows, an anchor jump on prepend, lost selection, broken thumb dragging, or a broken jump-to-latest.

## Beyond the chat pane

| Workload | What we know | What to measure next |
| --- | --- | --- |
| Background turns | The [router](../web/src/lib/events/router.svelte.ts) updates sidebar activity before chat filtering; [panel commits](../web/src/lib/chat/conversation/conversation-panel-registry.svelte.ts) select matching chat IDs. In six completed synthetic turns addressed to other visible tiles, five mutated only that tile and shared UI; one also recorded one mutation in an unrelated tile. With just one visible chat, three turns addressed to a non-tiled chat mutated shared UI only. [Counts](qa/webkit-spa-responsiveness/background-turns.csv). | Trace a live receiving tile while typing in another. Split time between incoming batch processing, row publication/measurement and style/paint. Compare actual token streaming with completed turns. A lack of DOM mutations doesn't exclude JS, style, or paint. |
| Large chat catalog | A complete [sidebar projection](../web/src/lib/sidebar/display/sidebar-row-model.ts) on 50 / 200 / 2,000 synthetic chats cost **0.9 / 1.9 / 16.5 ms in GTK** and **0.5 / 2.2 / 18.3 ms in Chromium**, without rendering a single row. Virtualizing its DOM doesn't remove grouping or sorting. | Measure *how often* a changed preview actually rebuilds that projection while the sidebar is visible and hidden. Separate row text from order/group changes if frequency warrants it. Preserve unread badges, grouping, sort order and anchor. |
| Keyboard routing and parked Files | [Visibility lookup](../web/src/lib/workspace/visible-presentations.ts) walks visible windows. Two lookups are possible for an unclaimed surface key. At twelve panes, one pure lookup cost **0.0025 ms in GTK**, not enough to explain a slow key on its own. [Workspace layout publication](../web/src/lib/workspace/workspace-services.ts) also rechecks every open file view; unchanged visibility needn't do I/O. | Compare a tab change with 1 vs 40 parked file views, count actual refreshes. Don't add a global cache for the keyboard microbenchmark. [Browser projection samples](qa/webkit-spa-responsiveness/projections.csv). |
| Terminals | [Parking the runtime](../web/src/lib/terminal/runtime/terminal-runtime.svelte.ts) stops fitting; [sequenced terminal output](../web/src/lib/terminal/sessions/terminal-registry.svelte.ts) can still reach xterm. A hidden silent shell isn't a busy log tail. No measured latency attributed here. | Compare an idle vs chatty hidden terminal at identical foreground layout. Count delivered bytes, xterm writes and foreground frame gaps. Preserve sequence, bounded backlog, scrollback and alternate-screen contents. |
| Git and Files together | A [file save](../web/src/lib/workspace/workspace-services.ts) invalidates Git at executor scope and schedules visible quick summaries; a [visible Git target](../web/src/lib/git/targets/git-target-session.svelte.ts) can rediscover an unrelated repo on the same executor. Not a cause of idle popup latency. | Save in repo A with repo B visible vs hidden; count B's requests and UI work. Narrow by known worktree identity only if the trace supports it; retain fallback for aliases and uncertain writes. |
| Streaming long history | An [earlier Garcon comparison](desktop-split-chat-performance.md) found deep reactive bookkeeping and copying on each append despite bounded DOM. At 3,000 rows/chat, Chromium batch p95 fell from 335 to 154 ms after an immutable-state change. This is a different workload from idle panes. | Repeat the existing split-chat endurance scenario in GTK with real foreground input, one vs several streaming chats, and a memory snapshot after closing panes. No evidence here of a leak. |

The [popup study](linux-webkit-pane-popups.md) remains a separate confirmed case: Bits' inherited body pointer lock made a local popup change style across the workspace; the full-viewport blur separately slowed Settings. Local hit-test backdrops helped. Removing the focus scan, forcing containment on every tile, and disabling all entrance animations didn't give comparable wins. The packaged .deb and AppImage and standalone GTK all reproduced the original popup problem. No new native window or Tauri IPC call is needed for these editor or feed interactions either.

## Practices worth borrowing

For iPhone, start with the [versioned WebKit performance guide and physical-device test matrix](qa/webkit-spa-responsiveness/webkit-iphone-performance-guide.md). It distinguishes a late input event, the wrong draft or caret, and missing scroll pixels; those need different measurements.

The [warm composer handoff follow-up](qa/webkit-spa-responsiveness/composer-handoff.md) found a full, unnecessary fit of the hidden Source textarea on eight of eight transfers. The guarded build skipped those fits and kept the visible fit. Two different Formatted changes failed a real WebKit geometry or typing check and were not shipped.

- **Start with latency, not bundle size.** [Optimize Interaction to Next Paint](https://web.dev/articles/optimize-inp) is a useful general guide: distinguish time waiting for the event, running its handlers, and presenting the result. Use [Web Inspector's Frames view](https://webkit.org/web-inspector/timelines-tab/#frames-view) for the WebKit equivalent of a rendering trace. An already-loaded SPA can fetch nothing and still miss its interaction budget.
- **Measure tasks, not a generic SPA score.** Slack publishes separate [launch, channel-switch and frame metrics](https://slack.engineering/unified-cross-platform-performance-metrics/) and distinguishes [visible content from completed work](https://slack.engineering/client-tracing-understanding-mobile-and-desktop-application-performance-at-scale/). For Garcon, mark current-pane feedback separately from “right draft accepts input.” Slack's [desktop client](https://slack.engineering/rebuilding-slack-on-the-desktop/) uses Electron; its [iOS engineering](https://slack.engineering/scaling-slacks-mobile-codebases-modernization/) describes native Swift/Combine. Slack in Safari is a relevant web comparison, but Slack.app on an iPhone isn't a benchmark of twelve web transcripts.
- **Keep work proportional to what changed.** Slack's [lazy client model](https://slack.engineering/making-slack-faster-by-being-lazy-part-2/) avoided full-cache synchronous storage work. Garcon already [debounces ordinary draft persistence](../web/src/lib/chat/composer/chat-draft-store.svelte.ts); don't blame a disk write on every key without a trace. Svelte 5's [derived values](https://svelte.dev/docs/svelte/$derived#Understanding-dependencies) can skip downstream work on equal output; [raw state](https://svelte.dev/docs/svelte/$state#$state.raw) helps large immutable collections. Apply these to measured invalidations, not every store. Move CPU-only parsing to a worker where justified, not focus, editing, or DOM layout.
- **Keep geometry reads together and CSS stable.** [CodeMirror's update cycle](https://codemirror.net/docs/guide/#update-cycle) separates DOM updates from a coordinated measurement phase. [Layout thrashing guidance](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing) and [WebKit's Speedometer investigation](https://webkit.org/blog/15249/optimizing-webkit-safari-for-speedometer-3-0/) explain why JS, text layout, selector resolution and rendering each matter. Localize frequently changing styles, limit the area of filters, and check actual layers rather than promoting every pane. Visibility isn't an excuse to unmount the user's draft.
- **Use native touch scrolling.** Since [iOS 13](https://webkit.org/blog/9674/new-webkit-features-in-safari-13/), overflow scrolling is already accelerated there. A global `-webkit-overflow-scrolling: touch` or JS momentum emulator isn't an upgrade. Garcon uses passive listeners and [defers incidental scroll corrections](../web/src/lib/virt/virtual-scroll-deviation.ts). [TanStack's real-device findings](https://github.com/TanStack/virtual/pull/1332) show why an explicit jump during momentum is a different operation from a row-height correction. Don't disable zoom, touch scrolling, focus traps, or accessibility announcements to improve a timing.
- **Choose metrics the engine actually supports.** [INP](https://web.dev/articles/inp) covers discrete interactions; “good” is at most 200 ms at the 75th percentile of visits, not a typing or scroll-frame budget. [Event Timing](https://www.w3.org/TR/event-timing/#sec-events-exposed) excludes continuous wheel/touchmove. [Safari 26.2](https://webkit.org/blog/17640/webkit-features-for-safari-26-2/) added Event Timing and native textarea field sizing; GTK 2.50.6 in this test exposed neither `event` entries nor `field-sizing: content`. Feature-detect. A double-rAF probe is neither INP nor proof of physical presentation. Browser engines differ by version and platform, not just JS runtime.

## Reproduce and set a budget

1. Use the production build, one OS window and synthetic chats from the [integration fixture](../integration-tests/support/integration-fixture.ts). Seed a balanced split tree with the [workspace reducer](../web/src/lib/workspace/workspace-layout.svelte.ts) as in the [endurance scenario](../integration-tests/tests/chromium/split-chat-endurance.test.ts). Keep the same twelve chats in the sidebar. Short fixture: one completed echo turn with 28 short paragraphs per chat. Scroll fixture: add 48 short, variable-length completed echo turns in the target chat. No live turn during timing trials. Measure idle and actual content, not skeletons.
2. These runs used WebKitGTK 2.50.6 MiniBrowser on X11/Xvfb with no GPU device and headless Chromium 156 on the same Linux VM, 1840 x 960 CSS pixels. Standalone results are not packaged-app, Brave, phone, or display-scanout timings. Discard trial zero per variant/block. The mode matrix alternated blocks in ABBA order (opposite orders per engine). In the stylesheet experiment, block 0 observed head changes; block 1 also instrumented editor methods. In the scroll experiments, alternate directions, compare like variants within a run, and verify input was actually delivered. GTK WebDriver required a fresh wheel input-source ID per notch to deliver repeated identical deltas. The Inspector trace used physical X11 input, a separate fixture and no screenshots. It is for attribution, not speed comparisons.
3. For a local sample, run the [one-interaction console probe](qa/webkit-spa-responsiveness/record-interaction.js) in the page's Inspector. Call `measureGarconInteraction('type')`, `('switch')` or `('scroll')`, close Inspector and perform the action within 30 seconds. For switch, click an inactive transcript, then repeat with an already-current one. Inspect `garconInteractionSample` afterward. It keeps only timing, flags and counts, never content or chat IDs. Type starts at `beforeinput` (or `input` if unavailable), so it is **not** the keydown-started laboratory metric. Scroll records the time to the first frame callback and the callback gaps fully between the first and last scroll events. An empty list means fewer than two callbacks in that interval, not a smooth scroll. Record multiple trials.
4. On the reporter's GPU-backed Linux desktop compare packaged Garcon, matching MiniBrowser and Brave on the same server/UI. Collect engine version, renderer (`webkit://gpu` in MiniBrowser), display backend, scale and refresh. A .deb uses the system engine; the AppImage may bundle a different one. For attribution record [Web Inspector Timelines / Frames](https://webkit.org/web-inspector/timelines-tab/) and [Layers](https://webkit.org/web-inspector/layers-tab/); repeat timings with Inspector closed. Cycle open/use/close and take [memory snapshots](https://webkit.org/blog/6425/memory-debugging-with-web-inspector/) before claiming a leak.
5. On a **physical iPhone**, [connect Web Inspector from a Mac](https://webkit.org/web-inspector/enabling-web-inspector/#ios-device). Test Safari and the actual app surface separately. The [mobile workspace](../web/src/lib/components/workspace/WorkspaceRoot.svelte) presents one chat; twelve saved desktop panes are not twelve visible iPhone feeds. Record model, OS, power mode, refresh, keyboard and zoom. Try normal typing and IME across line wraps, flick through history during a prepend, jump to latest mid-fling, open/close the keyboard and a dialog, and switch chats while another receives output. Verify caret, reading anchor, pinch zoom, and VoiceOver traversal. Linux WebKit or an emulated phone viewport does not validate these.
6. **Suggested product targets, not results:** on named reference hardware, p95 input-to-visible edit under 50 ms for ordinary typing, and p95 warm switch-to-correct-editable-draft under 100 ms; compare scroll frame intervals against that device's measured idle refresh period, including tails, blank rows and jumps. Report idle vs streaming, cold vs warm, desktop vs compact, 1/2/8/12 tiles and chat catalog size separately. Keep deterministic CI guards for stable sheets, bounded rows, correct drafts, and no unrelated updates. Use dedicated hardware or repeated paired runs for latency gates, not an absolute threshold in shared CI.

**Priority after the two fixes:** first reduce the measured work per scroll in the active transcript; second trace the receiving tile while typing in another and bound the work per update; third split and time the remaining focus and composer work on an already-visible pane switch. Recheck on GPU-backed Linux and test the corresponding compact workflows on a physical iPhone. Optimize the sidebar, terminals or Git invalidations only when the corresponding workload is present and its trace spends time there. No evidence here warrants replacing Tauri or Svelte.
