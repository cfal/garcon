# Formatted typing with unfinished Markdown labels

A long paragraph containing many `[` characters but no `]` did unnecessary work on every edit. The [text protection pass](../../../web/src/lib/components/chat/composer/composer-markdown-text.ts) checked each opening bracket against the whole remaining string to decide whether the Markdown serializer should escape it. The 24,000-character fixture contains 2,571 opening brackets. The new pass searches for the next `]` once and reuses its position (or the fact that none remains) until it passes it. The next character still decides whether the label could open a link, reference or definition. Leading punctuation and single tildes also no longer rescan prefixes on every occurrence. The rules and source-preserving block planner are otherwise unchanged.

**Native edit.** Production stock `d64f0b5d8` vs the same tree with only `composer-markdown-text.ts` changed. WebKitGTK 2.50.6 MiniBrowser, Xvfb, software rendering, compact 480 × 844, one chat, no concurrent turn. Median milliseconds; six measured keys per build and shape. These are DOM event and page-thread callback intervals, **not input-to-display times**.

| Single-paragraph draft | Keydown → input, stock / new | Keydown → second rAF, stock / new |
| --- | ---: | ---: |
| 250 characters, ordinary punctuation | 2.5 / 2.5 | 18.5 / 20.5 |
| 24,000 characters, ordinary punctuation | 32 / 40 | 59 / 67.5 |
| 24,000 characters, unfinished labels | 30 / 27 | **85.5 / 49** |

The benefit is specific to expensive label searches. The ordinary controls show no end-to-end gain; both have higher second-callback medians in this small run. A long ordinary paragraph can still feel slow. The software display, warm editor and physical-key driver do not establish iPhone keyboard, IME, paste, or display performance.

**Isolated serializer.** The [paired Bun benchmark](../../../web/scripts/benchmark-composer-labels.ts) runs the full edited-block codec in process and compares its output byte for byte. For the 250 / 4,000 / 24,000-character unfinished inputs, median stock → new ms were 0.072 → 0.056, 1.309 → 0.423 and **18.390 → 1.252**. Ordinary control medians were 0.074 → 0.070, 0.338 → 0.296 and 4.452 → 3.845. Nine alternating measured pairs per cell, one warm pair excluded. Separately, all 18,720 short punctuation/context comparisons produced identical protected text. Neither checksum equality nor Bun timings replace the browser test.

**Reproduce.** From the new checkout run `bun web/scripts/benchmark-composer-labels.ts /path/to/stock` against a stock source tree with its pinned dependencies. For the native comparison build both trees with `bun run build` and use identical copies of [the long-draft runner](../../../integration-tests/scripts/composer-long-draft.ts), [input probe](../../../integration-tests/scripts/composer-input-probe.ts) and [driver](../../../integration-tests/scripts/pane-benchmark-driver.ts) in both. In stock/new/new/stock order run `bun integration-tests/scripts/composer-long-draft.ts --webdriver=http://127.0.0.1:PORT --block=N`, with N from 0 to 3 and one exclusive GTK driver. Each invocation creates a fresh fixture and browser; shape order reverses in odd blocks. Each draft gets a full navigation, one warm edit and three measured edits at offset 6. Insert and remove `x` with native keys. All 48 insertions passed exact backing and visible text, owner, editor identity, focus, caret and settled-feed checks; all 48 deletions restored the starting draft and caret. [Per-key samples](composer-labels.csv).
