# Making SPA interactions responsive on WebKit and iPhone

Research checked **2026-11-23**. Start with the action that feels slow: **when did input arrive, when did the user see the right content, and when could they act on it?** A fast tap handler can leave the wrong draft on screen. A native scroller can move while JavaScript is busy and new pixels aren't ready. A fast first load says little about either. Measure each outcome separately.

**What we know about Garcon:** on software-rendered Linux WebKitGTK, typing into the same editor slowed much more when the chats *receiving* output were tiled than when they were absent. Removing a resting bubble shadow improved typical scroll callback gaps, but the faster build still showed gaps at two sampled output columns. Neither result is an iPhone measurement. Start on a real phone with typing during delivery, keyboard-driven layout changes, and a fling through a history prepend. The [interaction study](../../webkit-spa-responsiveness.md), [optimization controls](../../webkit-spa-optimization-results.md), [scroll and fullscreen study](../../webkit-scroll-and-fullscreen.md) and [virtualization sources](webkit-virtualization-references.md) supply the desktop controls, not mobile performance targets.

## Choose a measurement the client can make

| Question | Evidence to collect | Important boundary |
| --- | --- | --- |
| Why was a tap or key late? | [Event Timing](https://www.w3.org/TR/event-timing/): for a reported event, input delay is `processingStart - startTime`, dispatch time is `processingEnd - processingStart`; the remaining duration approximates time to the next rendering update. Group related events by nonzero `interactionId`; use the longest event, don't sum overlapping durations. | [Safari 26.2](https://developer.apple.com/documentation/safari-release-notes/safari-26_2-release-notes) added Event Timing and LCP in December 2025. Detect `PerformanceObserver.supportedEntryTypes.includes('event')` and `interactionId` on `PerformanceEventTiming.prototype` only after checking the interfaces exist. The default event threshold is 104 ms, minimum 16 ms; duration is rounded to 8 ms. An absent entry is not zero latency. |
| How responsive was a visit? | [INP](https://web.dev/articles/inp) covers clicks, taps and keyboard interactions, not scrolling, zoom or hover. It ignores one worst interaction per 50; the field target of at most 200 ms is at the 75th percentile of visits, segmented by device class. | One tap, five instrumented keys, a page-load LCP, or a lab p95 of callback intervals is not a site's INP. [CrUX](https://developer.chrome.com/docs/crux/methodology) includes desktop/Android Chrome, not iPhone Safari or even Chrome on iOS. No production telemetry is needed for these comparisons. |
| Did scrolling, selection or an edit **look** right? | Pair a visible item/caret and final state with input counts, movement and coverage through settle. For JS diagnostics record callbacks from *before* input through *after* the last scroll. In a second run inspect JS, style, layout, paint and layers. | rAF runs before rendering, not after physical presentation. Two callbacks, an observer notification, or a completed `img.decode()` do not certify the intended pixels. A phone filmed externally can show a visible stall, not identify its thread. |

**Do not translate engine version numbers.** The tested [GTK 2.50.6 source](https://github.com/WebKit/WebKit/blob/webkitgtk-2.50.6/Source/WebCore/page/PerformanceObserver.cpp#L151-L165) lists mark, measure, navigation, resource and conditional paint, not event entries. On clients without Event Timing use local event/ready marks and direct observation, not a fabricated INP. The checked compatibility data lists no Safari support for [Long Tasks](https://github.com/mdn/browser-compat-data/blob/2f696a2565efa5303ffd9e6a13365a0ef1a4f114/api/PerformanceLongTaskTiming.json), [Long Animation Frames](https://github.com/mdn/browser-compat-data/blob/2f696a2565efa5303ffd9e6a13365a0ef1a4f114/api/PerformanceLongAnimationFrameTiming.json) or [scheduler.yield()](https://github.com/mdn/browser-compat-data/blob/2f696a2565efa5303ffd9e6a13365a0ef1a4f114/api/Scheduler.json). Feature-detect on the actual target. Safari tabs, Home Screen web apps and a host's WKWebView have different chrome, lifecycle and insets. Record which one, the OS build and settings; browser branding is not an engine test ([Apple's alternative-engine entitlement in the EU](https://developer.apple.com/support/alternative-browser-engines/)).

## When input waits behind application work

**Keep immediate work small; defer the consequence, not the edit.** Apply the native edit, selection, correct draft ownership and immediate feedback first. Coalesce *derived presentation* such as rebuilding a sidebar or re-highlighting visible text, not ordered data, permission transitions, saves or terminal bytes. A later task can process a bounded batch, recheck the document/chat revision and cancel stale work. A worker is worth testing for pure parsing only when saved main-thread time exceeds startup and copying; it cannot read DOM layout.

The [HTML event loop](https://html.spec.whatwg.org/multipage/webappapis.html#event-loop-processing-model) drains microtasks before returning to other work. `Promise.resolve()`, `queueMicrotask` and Svelte [`tick()`](https://svelte.dev/docs/svelte/lifecycle-hooks#tick) are not yields to input or guarantees of paint. A timer schedules another task but may be delayed; rAF is for a bounded visual update, not an expensive parse just before paint. Keep activation-dependent operations such as opening a picker in the initiating gesture. Compare both first feedback and **time to correct usable data** so a later task cannot merely move the stall.

Garcon's [feed projection](../../../web/src/lib/components/chat/transcript/ConversationFeedProjectionState.svelte.ts#L225-L258) already has an incremental append path; [Files visibility](../../../web/src/lib/workspace/workspace-services.ts#L489-L503) and [xterm parking](../../../web/src/lib/terminal/runtime/terminal-runtime.svelte.ts#L153-L172) also exist. Test what still runs under actual delivery rather than suspending entire sessions. In an earlier 12-pane GTK test, median key-to-two-callbacks was **49 ms quiet, 51 ms with non-tiled recipients, 159 ms with tiled recipients** at about 3.3 completed turns/s. A [later build comparison](../../webkit-spa-optimization-results.md#production-build-comparison) improved the busy-key median from 98 to 31 ms in its own run. Neither measured tokens arriving individually or an iPhone keyboard. The [sidebar measurements](../../webkit-spa-optimization-results.md#large-sidebar) timed complete projections, not their frequency in a real session.

## When style, geometry or text dominates

* **Measure one layout, not a succession of dirty layouts.** A geometry read after DOM/style writes can force earlier invalidations to be resolved synchronously. Read the required boxes together, then write differences; narrow which subtree a change dirties in the first place. [CodeMirror's update cycle](https://codemirror.net/docs/guide/#update-cycle) deliberately separates DOM writes and a measure phase; integrate via `requestMeasure`, not a competing read in an update callback. [ResizeObserver](https://www.w3.org/TR/resize-observer/) delivers measured sizes, not free synchronous initial geometry; mutating the observed size again can cause another layout/delivery. In Garcon's [fullscreen attribution](pane-fullscreen-attribution.md), supplying the correct cached width moved the delay to the *next* read. The [observer-only control](../../webkit-spa-optimization-results.md#alternatives-not-shipped) did not improve wheel timing. Preserve prepaint coverage and the post-commit anchor check.
* **Limit rendered work without losing identity.** [Svelte keyed lists](https://svelte.dev/docs/svelte/each) preserve identity across inserts/moves; use a durable item key, not a changing array index. Keys don't make a thousand live components cheap. [CodeMirror](https://codemirror.net/docs/guide/#viewport) renders a viewport plus a margin and retains document height information. [Garcon's transcript](../../../web/src/lib/components/chat/transcript/ConversationFeed.svelte) and [Git diff](../../../web/src/lib/components/git/GitVirtualDiffViewport.svelte) already window their DOM. Putting another virtualizer around an editor or recycling a focused node for a different message risks wrong caret, selection, search results and VoiceOver order.
* **CSS skipping is different from removing DOM or suspending JS.** [Safari 17](https://developer.apple.com/documentation/safari-release-notes/safari-17-release-notes) added `contain-intrinsic-size`; [18](https://developer.apple.com/documentation/safari-release-notes/safari-18-release-notes) added `content-visibility`; [26.0](https://developer.apple.com/documentation/safari-release-notes/safari-26-release-notes) fixed Find on Page for skipped `auto` content. [CSS Containment](https://www.w3.org/TR/css-contain-2/#relevant-to-the-user) distinguishes near-screen, focused and selected content from skippable content; `auto` must retain find, focus and selection semantics. Try it on a *long, genuinely offscreen, non-virtualized section*, with a realistic intrinsic placeholder and an unchanged fallback. Layout queries can defeat the saving. Paint containment can clip overflow and change positioning; a modal covering visible tiles doesn't make them offscreen. Don't put it on every pane or assume CSS suspends subscriptions.
* **An editor's job ends at the correct caret, not the first painted shell.** [Input Events Level 2](https://www.w3.org/TR/input-events-2/) distinguishes IME composition from cancellable edits; [ProseMirror exposes composing state](https://prosemirror.net/docs/ref/#view.EditorView.composing). Let the IME own marked text: don't replace the editable DOM, send on composing Enter, or restore an obsolete selection mid-composition. Compare [Source and Formatted](../../../web/src/lib/components/chat/composer/ComposerInputSurface.svelte), collapsed/expanded and cold/warm fonts. [FontFaceSet.ready](https://www.w3.org/TR/css-font-loading-3/#font-face-set-ready) can stabilize a *warm test*; don't gate the app on all fonts. A fallback-to-final font change can rewrap lines and change anchors. Exercise paste, dictation or autocorrect, undo, emoji, bidi and a composing keyboard. [Safari 27](https://developer.apple.com/documentation/safari-release-notes/safari-27-release-notes) documents an IME dispatch-order fix for Devanagari and other input methods; synthetic Latin keydowns on Linux cannot cover this.

Two narrowly relevant version checks: [Safari 26.2](https://webkit.org/blog/17640/webkit-features-for-safari-26-2/) supports native textarea `field-sizing: content`. Compare with the existing Source-mode sizing at the same min/max height; preserve a fallback and don't apply textarea results to rich `contenteditable`. [Safari 27](https://developer.apple.com/documentation/safari-release-notes/safari-27-release-notes) fixed increasingly sluggish ResizeObserver callbacks and quadratic iteration with many IntersectionObserver targets. That justifies recording version and observer target count, not blaming observers for our GTK timing or removing them.

On iPhone distinguish the **layout viewport** from the part the user can actually see. The [Visual Viewport API in Safari 13](https://webkit.org/blog/9674/new-webkit-features-in-safari-13/) accounts for both pinch zoom and the onscreen keyboard; a resize isn't proof of keyboard visibility. Garcon's [binding](../../../web/src/lib/components/layout/mobile-viewport-binding.ts#L18-L60) already coalesces resize/scroll events into rAF, then sets root CSS variables using a [height/offset heuristic](../../../web/src/lib/components/layout/mobile-viewport.ts). Compare redundant *applied values* and which descendants re-layout before adding another listener. Keep safe-area insets, pinch zoom, large text, an external keyboard and rotation working; neither a constant keyboard height nor `100dvh` alone establishes caret visibility.

## When scrolling moves but pixels arrive late

**Separate event delivery, position and paint.** Since iOS 13, [WebKit accelerates overflow scrolling](https://webkit.org/blog/9674/new-webkit-features-in-safari-13/); the old `-webkit-overflow-scrolling: touch` is unnecessary and the release note identifies an iPhone stacking-context side effect. Let the native scroller handle momentum. Use [passive listeners](https://webkit.org/blog/8216/new-webkit-features-in-safari-11-1/) for observational touch/wheel work so scrolling need not wait for cancellation; passive doesn't make a slow handler cheap. Do not mark a handler passive if it must cancel a gesture. Keep native selection, pinch zoom, nested menu scrolling and keyboard scrolling. [Garcon's driver](../../../web/src/lib/virt/virtual-list-dom-driver.ts) already observes scroll intent passively and [defers incidental offset corrections](../../../web/src/lib/virt/virtual-scroll-deviation.ts) while scrolling, unlike an explicit jump-to-latest.

WebKit may raster tiles outside the viewport to keep up with scrolling. [Layers/paint flashing](https://webkit.org/web-inspector/layers-tab/) distinguishes repaint work from recompositing existing backing stores; more layers can cost significant memory. Test the smallest repeated visual effect (shadow, blur/backdrop, filter, translucent overlapping surface) at unchanged dimensions on **real content**. If only movement is intended, test transform/opacity versus relayout, but don't assume a transform is free or force a layer on every item. The [CSS will-change specification](https://www.w3.org/TR/css-will-change-1/#dont-global) cautions against overuse. For overlays, [Garcon's popup controls](../../linux-webkit-pane-popups.md) identified a cost from fullscreen blur and inherited body styles; eliminating a dialog focus scan did not improve the measured opening. Keep the keyboard trap and pointer backdrop.

The [final product comparison](../../webkit-scroll-and-fullscreen.md) found GTK's typical within-train callback gap went **99 to 44.5 ms** for paragraphs and **83.75 to 40.25 ms** for mixed Markdown after removing only a closed user bubble's shadow. The [independent columns](scroll-row-paired-stripes.md#final-product-builds) still showed a common band up to 649 px in one candidate down train; these were sequential samples of marked columns, not a whole blank pane or physical frames. Even retaining all real rows produced a missed band in a different control. Neither bigger overscan nor changing all transforms to `top` follows. On Linux, match WebKitGTK version, [acceleration policy](https://webkitgtk.org/reference/webkit2gtk/stable/enum.HardwareAccelerationPolicy.html), actual renderer, display backend and viewport before comparing. A policy permitting acceleration is not evidence of an active physical GPU. Neither GTK raster timings nor a narrow desktop Playwright viewport represent iPhone touch or Core Animation.

## When cold loading, memory or idle work dominates

**Load what enables the next action.** Split editor/language tooling behind intent, but inspect the network waterfall on first actual use: serial imports can make first-open slower. Compare cold navigation, first pane open and warm revisit separately. In its [Facebook web redesign](https://engineering.fb.com/2020/05/08/web/facebook-redesign/), Meta tiered resources into shell, visible content and later work, warning against a waterfall of child imports discovered during render. Slack's [desktop history deferral](https://slack.engineering/making-slack-faster-by-being-lazy-part-2/) reduced the need to fetch every conversation, but forced them to fix unread markers and restored scroll positions. Slack's [visible vs usable definitions](https://slack.engineering/unified-cross-platform-performance-metrics/) are useful; their TTU meant current content displayed, not a tested keystroke. These are first-party **design accounts**, not iPhone Safari benchmarks: Slack's [mobile codebase](https://slack.engineering/scaling-slacks-mobile-codebases-modernization/) and [Electron desktop app](https://slack.engineering/rebuilding-slack-on-the-desktop/) are different clients.

**Separate transfer, decode and display.** Size thumbnails for their rendered size and device pixel ratio (`srcset`/`sizes` when variants exist); reserve aspect ratio before decode. [HTML image decoding](https://html.spec.whatwg.org/multipage/embedded-content.html#dom-img-decode) signals readiness, not a visible frame, and decoded data may be evicted. Lazy-load *offscreen* images ([Safari 15.4](https://developer.apple.com/documentation/safari-release-notes/safari-15_4-release-notes)); don't defer the one the user just opened. Fetch Priority is a hint ([Safari 17.2](https://developer.apple.com/documentation/safari-release-notes/safari-17_2-release-notes)), not a reason to prioritize everything. Garcon's [image cache](../../../web/src/lib/files/images/file-image-cache.svelte.ts) already queues work and [decodes](../../../web/src/lib/files/images/decode-file-image.ts); the [attachment store](../../../web/src/lib/chat/composer/image-attachment.svelte.ts) owns object URLs. Compare bytes, dimensions, concurrent decodes and memory after close/reopen, not just JS heap or time to request completion. Don't revoke a preview a reader is still using.

**Make inactivity genuinely quiet, but keep durable state correct.** A background page, a parked pane inside a visible page, and an unfocused *visible* pane are three different workloads. [WebKit's power guidance](https://webkit.org/blog/8970/how-web-content-can-affect-power-usage/) describes throttled timers, suspended rAF and possible iOS tab suspension. Batch nonurgent wakeups; don't rely on periodic callbacks to save data or fake catch-up by replaying every animation. Garcon has [draft-flush](../../../web/src/lib/chat/composer/chat-draft-store.svelte.ts) and [socket resume](../../../web/src/lib/ws/connection.svelte.ts) hooks. Verify one correct reconciliation after return, no stale draft or duplicate read receipt. [WWDC19's CPU timeline walkthrough](https://developer.apple.com/videos/play/wwdc2019/513/) shows how to compare interaction time with the return to idle. On supported iPhones [ProMotion](https://developer.apple.com/documentation/quartzcore/optimizing-iphone-and-ipad-apps-to-support-promotion-displays) is adaptive up to 120 Hz; Low Power Mode and heat can disable faster rates. This is native display guidance, **not** a Safari rAF contract, a JavaScript power sensor, or a plist setting a website can use.

## What to test first

These are **proposed comparisons**, not new results. Change one variable per pair. For each, log actual workload, first visible feedback, correct usable state, and failures. Keep later tests only if the first observation identifies their bottleneck.

| Priority and symptom | Matched comparison | Discriminator and rejection condition |
| --- | --- | --- |
| 1. Typing under delivery | Same short draft, focused editor and recipients. Quiet vs fixed-rate delivery to a non-presented chat on compact iPhone; on desktop, also deliver the same stream to visible tiles. Separate completed-turn and token-stream blocks. [Projection](../../../web/src/lib/components/chat/transcript/ConversationFeedProjectionState.svelte.ts) and [sidebar grouping](../../../web/src/lib/sidebar/display/sidebar-order-controller.svelte.ts). | Count actual deliveries and projection/DOM updates per recipient **apart from** the uninstrumented tap/key pass. If parked delivery is equally slow, trace shared sidebar/transport before optimizing visible rows. Reject lost output, out-of-order permissions or delayed focused text. |
| 2. Keyboard and pane transfer | Tap already-active chat vs switching to a chat with a distinct synthetic draft, with software keyboard closed then open. Repeat separately in Source/Formatted; one run with pinch or larger text. [Viewport binding](../../../web/src/lib/components/layout/mobile-viewport-binding.ts) and [formatted editor](../../../web/src/lib/components/chat/composer/ComposerMarkdownEditor.svelte). | Record first feedback, correct draft/caret, and whether an immediate edit lands in the right chat. Count root style changes vs actual metric changes only in the trace. Reject a focus jump, lost composition, retained keyboard gap or obscured Send. |
| 3. Visible scrolling | Same tall transcript, font, starting item + offset and geometry. Fling both ways on the phone, first with history settled, then across a held/released prepend. For a graphic change A/B one effect only; never use light placeholders as the candidate. [Row evidence](row-entry-rendering.md). | Track a numbered row during motion, any exposed/stale content and where a tap lands after release. Record displacement and both interval edges; unequal travel is not a matched speed test. Reject worse coverage, anchor drift, lost selection or broken jump-to-latest even with faster callbacks. |
| 4. First open vs warm revisit | From the same empty workspace open a fixed synthetic image or a file of one language; repeat warm. Compare just image source size **or** first-use import scheduling. [File image cache](../../../web/src/lib/files/images/file-image-cache.svelte.ts), [language loading](../../../web/src/lib/highlighting/codemirror-language-registry.ts). | Mark shell, usable editor/decoded visible image, bytes and memory after several closes. A smaller network waterfall with a slower first edit is a loss. Preserve alt text, correct revision, zoom and error/cancel behavior. |
| 5. Idle and offscreen | After identical work, leave foreground idle, park the pane, then background the app for a fixed interval; measure resume separately. Only if offscreen layout dominates, compare one long [Shortcuts settings section](../../../web/src/lib/components/settings/KeyboardShortcutsSection.svelte) with/without CSS skipping and a measured placeholder. | In the trace count wakeups, paints and reconciliations. In uninstrumented runs compare first usable state after return/scroll. Reject skipped shortcuts in Find, keyboard or VoiceOver navigation, missing terminal protocol responses, changed reader position, or a burst of stale updates. |

## Physical iPhone, offline and without a debugger

1. Use a disposable profile and **synthetic** numbered rows, throwaway drafts, images and fake local delivery. Use the same prepared builds/fixture on a private LAN with WAN disconnected and cellular data off; no public tunnel, external providers, analytics or real account. Verify a fresh reload works on that LAN. On a phone, `localhost` is the phone, not the laptop. For a strictly radio-off run, use an already installed self-contained fixture and verify its data survives relaunch first. Garcon's [service worker](../../../web/src/service-worker/index.ts) caches a shell but deliberately bypasses `/api` and `/ws`: shell availability alone does not make authenticated history or delivery offline.
2. Record iPhone model, OS build, Safari tab/Home Screen/WKWebView, orientation, font/text size, zoom, Reduce Motion, power/charge and temperature condition. Keep content, settings, network and start anchors identical within pairs. Start cool; don't force a refresh rate or change accessibility settings to get a better number. Do **not** attach Inspector or enable screen capture for the baseline. Make one cold observation separately; alternate warm A/B then B/A, for example three pairs per order. Keep misses and failed actions. Report per-action readings, count, median and range, not a population tail.
3. With no Mac required, operate with a finger. Type a known character, switch between two distinct drafts, fling past a numbered row, or focus/dismiss the software keyboard. Score first feedback and **correctness** by a second action: verify the intended character, caret and owner, or select the intended row after scrolling. An observer can record pass/fail and conspicuous pauses. For latency, film finger and screen together using a second device at a known rate, offline with notifications hidden; bracket contact and first visible change by adjacent camera frames. Keep only counts/timings; erase the synthetic clip locally. Camera sampling/rolling shutter and human gestures limit precision. Without timed capture, report observations, not milliseconds.
4. Repeat the interaction with VoiceOver (swipe/rotor order after a prepend, current item and focus after closing), keyboard navigation, larger text/pinch and Reduce Motion. Check [WCAG text resizing](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html) and [reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html). Never disable page zoom, falsify `aria-hidden`, silence required announcements or remove the focus trap for a speed score.
5. **Only for attribution**, repeat the same short case on the same phone with a Mac: [enable Web Inspector](https://webkit.org/web-inspector/enabling-web-inspector/) on the phone and Mac, connect a trusted cable, choose the device and page in Safari's Develop menu. A [WKWebView must allow inspection](https://webkit.org/blog/13936/enabling-the-inspection-of-web-content-in-apps/): the per-view opt-in defaults off for apps linked against the iOS 16.4+ SDK; do not enable this on customer installs for this test. In [Timelines](https://webkit.org/web-inspector/timelines-tab/) record JS & Events, Layout & Rendering and Rendering Frames; use a **separate** CPU/idle, Layers or memory capture when needed. Correlate tasks with invalidation, geometry flush, paint and requests; do not sum nested durations or assign unexplained intervals to GPU/GC. Detach and repeat the uninstrumented pair. A non-inspectable device is still useful for steps 1-4.

**Evidence limit:** published engine behavior and production accounts motivate the matrix; the linked Garcon studies measured only their named builds, workloads and renderers. No physical iPhone, WKWebView, GPU-backed Linux, power measurement or new benchmark was run for this guide.
