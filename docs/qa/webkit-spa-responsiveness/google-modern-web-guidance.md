# What Google's Modern Web Guidance adds to the Garcon investigation

Checked 2026-11-24. The most useful advice is to **separate work already blocking an input, work done by its handlers, and work delaying the next rendered update**. For Garcon, add a fourth question: *did the next edit actually reach the intended draft?* Google does not provide a WebKit virtualizer fix or a performance result for this app.

**Source.** [Chrome's official documentation](https://developer.chrome.com/docs/modern-web-guidance) identifies [GoogleChrome/modern-web-guidance](https://github.com/GoogleChrome/modern-web-guidance) as the distribution; `modern-web-guidance-src` is its authoring repository. I inspected a depth-one clone at **`2b4aa13a72dd47cd135b06ce5abfccd92e19b24f`, “Release v1.0.2,” 2026-11-23**. The [README](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/README.md#L5-L11) credits Chrome, Edge, Firefox, MDN and the community. This is deliberately concise [platform and fallback guidance](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/README.md#L34-L47) for generated code, not a browser conformance suite. I searched the [guide tree](https://github.com/GoogleChrome/modern-web-guidance/tree/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/skills/modern-web-guidance/guides) and read the relevant performance, form, dialog and scrolling entries as documents; nothing was installed or invoked.

## Two discriminating experiments

1. **Visible recipient: separate model updates from publishing the row.** Google's [INP diagnostic](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/skills/modern-web-guidance/guides/performance/identify-inp-causes.md#L3-L18) separates handler-forced style/layout from subsequent rendering. In Garcon's [four-pane GTK study](composer-input.md#steady-typing), **44 vs 109.5 ms was keydown to second rAF**, not input delay or input-to-paint. Keydown to native input was **5 vs 3.5 ms**. Calculating `two_raf_ms - input_ms` per key in the [stock CSV](composer-input.csv) gives **38.5 vs 106.5 ms from observed input to second rAF** (medians, eight warm keys each). Seven receiving trials saw assistant receipt after input and the new row in the DOM before the second callback. Compact keydown to second rAF was 21.5 vs 23.5 ms with no presented recipient.

   Try the *same four visible panes* and wire payload: accept every update into the cache in both arms, but put just the non-owner's derived [feed publication](../../../web/src/lib/components/chat/transcript/ConversationFeedProjectionState.svelte.ts) in one later task in the diagnostic arm. Mark wire receipt, projection completion, DOM publication and next callbacks. Verify that publication actually crossed the key's observation window; a scheduled timer alone proves nothing. Use a separate GTK Inspector trace to distinguish JS, style and layout. Score recipient time-to-visible **as well as** foreground input, final order, read state and anchor. If only the recipient becomes late, the change merely moved the stall. [Fewer copied map entries](visible-receiver-projection.md) are already established, not a millisecond explanation.
2. **Phone momentum: compare two end signals without changing scrolling.** The guide [distinguishes `scrollend` from debounced guesses](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/skills/modern-web-guidance/guides/performance/defer-work-until-scroll-ends.md#L3-L16); [Safari 26.2](https://developer.apple.com/documentation/safari-release-notes/safari-26_2-release-notes) added the event. Garcon already [resets a 200 ms settle timer while touch coasts](../../../web/src/lib/chat/transcript/conversation-native-scroll-settlement.ts#L25-L75). On a supporting physical iPhone, passively timestamp the actual feed element's native `scrollend` beside the existing switch to idle for a fling, interrupted fling, and no-movement tap. Keep both observation-only; compare ordering against a pending prepend and actual numbered reading anchor. Keep the existing cancellation/fallback for unsupported engines or absent events. Don't defer visible row mounting, thumb feedback, focus or explicit navigation to `scrollend`. A desktop wheel train doesn't exercise this touch state machine.

## What not to repeat or ship

| Existing evidence | What the guidance does and doesn't support |
| --- | --- |
| **Compact drawer:** stock lost the first native key on 1/4 different-chat selections. In a [separate marked build](composer-input.md#why-an-eligible-editor-missed-the-key), the correct Source box was eligible before keydown on two lost moves; the first scheduled rAF came after it. | [Next paint can be only a shell or spinner](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/skills/modern-web-guidance/guides/performance/interaction-paint-timing.md#L3-L9). Keep the existing strict key-target/caret/other-draft guard when trying earlier delivery of **already requested** focus after commit; don't steal deliberate pointer focus, bypass a modal, or replay global keys. The [IME guide](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/skills/modern-web-guidance/guides/forms/ime-safe-enter-submit.md#L51-L75) supports checking composition and Safari's historical 229 case, not cancelling candidate confirmation unconditionally. On a phone, select via tap and VoiceOver, type immediately, confirm a Japanese candidate without sending, then dismiss via Escape with a keyboard. Verify announced focus, visible caret and correct draft. |
| **Unfinished Markdown:** at 24k characters the [linear label scan](composer-labels.md) took GTK keydown-to-second-callback from **85.5 to 49 ms**; long ordinary text was **59 to 67.5 ms** in the same small comparison. | Google's [time-sliced loop](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/skills/modern-web-guidance/guides/performance/break-up-long-tasks.md#L11-L39) is not an alternative to eliminating repeated scans. Its 50 ms example is a long-task threshold, not a typing/frame budget. Neither `scheduler.yield()` nor [priority scheduling](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/skills/modern-web-guidance/guides/performance/schedule-tasks-by-priority.md#L51-L71) is a Safari dependency to introduce; a timer yields a task, not guaranteed paint or priority. Don't defer canonical draft updates, selection or submit behind it. |
| **Scroll paint:** dropping one resting shadow improved the [product callback gaps](../../webkit-scroll-and-fullscreen.md); the faster build still exposed up to **649 px at two sampled columns** in one down train. Both endpoints being correct did not ensure painted coverage. | The [reordering guide](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/skills/modern-web-guidance/guides/ui-behaviors/dynamic-sort.md#L102-L107) recommends batching DOM moves and suggests windowing very large lists, not a universal row threshold, overscan size or tile-damage fix. [Visible regions aren't skipped](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/skills/modern-web-guidance/guides/performance/interactions-in-complex-layouts.md#L9-L23); the [offscreen guide](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/skills/modern-web-guidance/guides/performance/defer-rendering-heavy-content.md#L15-L34) targets a different workload. [Viewport/row containment, track removal and larger windows](feed-scroll-scheduling.md) did not establish a repeatable production improvement. Don't promote every row or hide searchable content; preserve find, focus, selection, geometry and an independent output check. |

**Portability and profiling.** Detect entry types on the actual runtime. Google's [compatibility table](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/skills/modern-web-guidance/guides/performance/identify-inp-causes.md#L90-L105) puts Event Timing in Safari 26.2 but Long Animation Frames in Chromium, not Safari. The [soft-navigation and interaction-contentful-paint entries](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/skills/modern-web-guidance/guides/performance/interaction-paint-timing.md#L178-L199) are likewise not a GTK/Safari measurement plan. [GTK 2.50.6's entry list](https://github.com/WebKit/WebKit/blob/webkitgtk-2.50.6/Source/WebCore/page/PerformanceObserver.cpp#L151-L165) doesn't even include `event`. Use local milestones and a separate [Web Inspector recording](https://webkit.org/web-inspector/timelines-tab/); do not send selectors, text, script URLs or telemetry. API absence isn't zero delay, rAF isn't physical presentation, and load-time LCP, preloads or speculative navigation don't diagnose a key in an already-warm chat.

One version trap: Google's [combined feature table](https://github.com/GoogleChrome/modern-web-guidance/blob/2b4aa13a72dd47cd135b06ce5abfccd92e19b24f/skills/modern-web-guidance/guides/performance/interactions-in-complex-layouts.md#L62-L75) says Safari 26 for `content-visibility`; Apple records the property in [Safari 18](https://developer.apple.com/documentation/safari-release-notes/safari-18-release-notes) and a skipped-content Find fix in [26](https://developer.apple.com/documentation/safari-release-notes/safari-26-release-notes). Syntax support isn't behavior parity. No dedicated iOS variable-height virtualization or soft-keyboard focus-handoff algorithm was found in this release. See the [offline iPhone procedure](webkit-iphone-performance-guide.md#physical-iphone-offline-and-without-a-debugger) and [upstream tile evidence](webkit-virtualization-references.md). This was source research, not a new timing or device test.
