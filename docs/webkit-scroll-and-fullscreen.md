# What makes the transcript slow to scroll?

On Linux WebKitGTK, the **resting box shadow on ordinary user-message bubbles** was one substantial, removable cost of scrolling a tall transcript. The app now omits that shadow only while an ordinary bubble's menu is closed. With no diagnostic styles on either build, the typical callback gap fell from **99 to 44.5 ms** on paragraphs and **83.75 to 40.25 ms** on mixed Markdown. Repeated samples still showed some missing output pixels on the faster build. [Matched experiments, interaction checks and residual gaps](qa/webkit-spa-responsiveness/row-entry-rendering.md).

The investigation started with two broader controls on the old rendering: leaving all real rows mounted, or giving the virtualizer cheap rows of the correct size. Neither is a production fix. The following experiments separate the cost of drawing actual rows, missing output pixels and fullscreen transitions; improving one does not prove the others are fixed.

## Same gesture, different row work

Each cell below gives two numbers in milliseconds: the **typical callback gap** and the **typical worst gap per gesture**. Compute the median and maximum inside each warm wheel train, then take the median of each statistic across trains. Each gesture has equal weight. These are page-thread animation-frame callbacks, not physical display frames.

| Single 1520 x 806 feed | WebKitGTK 2.50.6 | Chromium 156 |
| --- | ---: | ---: |
| Normal range, real message content | **129 / 215** | 16.8 / 32 |
| All 100 virtual items mounted, real content | **18 / 71** | 17.1 / 27 |
| Normal range, entering messages replaced by measured empty rows | **19 / 50** | 16.9 / 22 |

Normal GTK was slower in **all three** interleaved control blocks: typical gaps of 108, 147 and 140 ms. Its worst observed gap was 614 ms, not its usual gesture. Even retaining all the real rows had a 210 ms outlier. Chromium stayed near its ordinary callback cadence in all three conditions. The difference isn't a benchmark of JavaScriptCore versus V8: row creation also exercises style, layout, paint, and browser scheduling.

All 98 GTK/Chromium trains delivered exactly 14 trusted pixel-mode wheel events and moved the feed exactly 1,680 CSS pixels. Every down train went from item 46 at -5 px to item 67 at -1 px; every up train went from item 66 at -5 px to item 45 at -31 px. These are two separately anchored directions, not an exact reverse. Retaining the whole transcript changes how much earlier content has been measured, so absolute scrollTop is *not* a comparable anchor. At both ends of every warm lightweight-row train, the mounted messages were placeholders. Across all 56 sampled lightweight endpoints, none of 1,604 wrapper-size comparisons was missing or off by even one pixel.

**What this isolates:** with the same native viewport, wheel handler, Virt range calculations, scroll thumb and movement, mounting 20 or 21 cheap wrappers didn't reproduce the large delays. Keeping real content present without repeatedly constructing it also avoided the usual delays. This implicates the real row lifecycle and its rendering cost, **not** pure virtual range arithmetic, Tauri IPC, or one proven JavaScript function. The lightweight control also removes painting real text and interactive descendants; it does not distinguish JavaScript construction from their style and rendering costs.

**Why not retain everything?** Even with only 98 entries plus two structural items, the retained control mounted 100 wrappers at initial readiness instead of 17. GTK document setup was 2.36 to 2.46 s in those two blocks versus 0.82 to 1.26 s in the three normal blocks. That includes navigation, data readiness and settling, not an isolated row-mount timer or a memory benchmark. Retaining long histories in every pane would move work into opening and resizing and defeat the purpose of virtualization.

## Where the time went

On the unpatched production build, an attached GTK Inspector recorded a real wheel train over the same feed. Four calls to [the collapsible message's first height read](../web/src/lib/components/chat/transcript/rows/CollapsibleBody.svelte#L36) synchronously triggered **30.92 ms of style recalculation and 5.12 ms of layout** in aggregate. A scrollbar offset read triggered another 6.78 ms of style calculation. The longest complete Inspector rendering frame was 54.76 ms, including a 37.17 ms scroll dispatch; 11.63 ms style and 1.39 ms layout inside that dispatch occurred at the disclosure read. A browser often charges earlier dirty work to the read that flushes it. Deleting the read need not save all that time.

That trace **does not explain the whole stall**. In its longest 180.04 ms interval between two page callbacks, 134.76 ms lay outside timed Inspector records. No recorded GC overlapped it. Unknown time is not evidence that the compositor, Tauri, GC or the host scheduler was responsible. Inspector was attached, the standalone MiniBrowser used physical-style X11 notches (14 events, 1,358 px), and this is one train, not another cell of the timing matrix. [Disjoint trace accounting and generated call sites](qa/webkit-spa-responsiveness/gtk-scroll-inspector.json).

The [separate diagnostic counter runs](qa/webkit-spa-responsiveness/scroll-row-counters.csv) distinguish virtual measurement from work inside message components. In the two warm GTK normal trains, 20/21 wrappers attached, their observed sizes matched the cache, no uncached prepaint row measurement or fallback offsetHeight read ran, and Virt's synchronous native-scroll handler returned in 5/8 ms **total**. This narrow timer excludes subsequent reactive flush, rendering and paint. The first down warm-up did measure 14 previously uncached rows. Cached remounts still need actual message components; removing their contents while retaining the wrappers was the much stronger control.

**Was the disclosure read itself the fix? No.** On the production page, capture the native clientHeight, clientWidth and scrollHeight of all 49 disclosure bodies at the fixed width, keyed by full virtual item and body ordinal. Then wrap the same getters in both conditions, either passing through to the native getters or returning the known dimensions for those bodies only. Other elements always pass through. After each train verify native dimensions, disclosure controls, all mounted keys and viewport-relative rectangles. An initial setup comparing a measured checkpoint with a warm-up was rejected. The final native/cached/cached/native comparison used one settled page and matched even the absolute scroll offsets.

Returning the known values eliminated 504 targeted native reads across the eight measured cached trains, without one fallback or changed disclosure. Nevertheless the typical gap / typical worst gap was **112 / 250 ms native, 167 / 315 ms cached**. Do not conclude caching generally slows GTK: this is a small, noisy counterfactual with identical getter wrappers, not a tuning technique. It is evidence **against treating that isolated read as the remedy**. [All disclosure trains, edge intervals and integrity checks](qa/webkit-spa-responsiveness/scroll-disclosure-gtk.csv).

## Did the display show gaps?

Sometimes, at the sampled column. A second process independently read a **1 x 806 pixel column from the Xvfb root** at a nominal 80 Hz. Diagnostic CSS marked the sizer background and each real row in contrasting colors without changing the measured layout. A stationary negative control was fully covered; hiding one 64 px row marker produced exactly a 64 px band at the expected position; restoring it removed the band.

In three downward production trains, **52 of 370 readings** showed some sizer. Each train had consecutive readings showing only sizer over the full 806 px height. Every affected read fell inside the wheel dispatch window. None of the 376 readings from the three upward trains showed an uncovered pixel. In the separate diagnostic build, normal showed smaller bands in both directions: this is **not** an established direction-specific bug.

Keeping all rows mounted did **not** guarantee coverage. In one of four retained-control trains, 22 readings wholly inside wheel dispatch showed an exposed band up to 120 px high. All 100 original wrappers remained at both endpoints, including the 98 real messages, and this control did not remove off-range rows. A missed paint at this strip therefore does not require virtual row entry. The slower real-row callbacks and the sampled painting gaps need separate acceptance tests.

The marker CSS can affect painting. A missing color in one column is neither proof of missing DOM nor a screenshot of a blank full-width pane. Gaps between X11 reads, stale content with the right marker color, and physical presentation remain unobserved. Don't turn a sample count into dropped frames or a continuous blank duration. [Pixel detector, positive control and samples](qa/webkit-spa-responsiveness/scroll-row-stripe.md).

## Fullscreen is separate

The [pane fullscreen study and samples](qa/webkit-spa-responsiveness/pane-fullscreen.md) used the real titlebar button, not the browser Fullscreen API. At one, four and twelve panes, GTK medians from trusted input to two frame callbacks were **103, 276, 527 ms entering**, and **106, 298, 650 ms exiting**. Chromium's twelve-pane results were **72 and 141 ms**. The sidebar collapses even for one pane, so the one-pane control is not a complete geometry no-op.

Every panel and feed stayed connected; eleven hidden panes became inert, no hidden pane acquired command ownership, the Source draft and selection survived the keyboard toggle, and the detached reader and end pin returned with zero observed drift. A hidden recipient also received and later displayed a real synthetic reply. **A full feed remount is not required for the slowdown.** Exit does re-enable visible projections, geometry observers and scroll restoration across eleven panes. That is a separate profiling target, not a measured breakdown of the 650 ms.

**Is it expensive just to keep eleven hidden panes?** After entering fullscreen and letting the workspace settle, the active production feed was exactly 1840 x 806 in both cases. With one pane the typical callback gap / typical worst gap was **119 / 205 ms**; with twelve retained but only one presented it was **109 / 197 ms**. Twelve warm gestures per condition. One driver session had to be replaced; a supplemental twelve-pane block and the final one-pane block in the same fresh session measured **118 / 243** and **126 / 241 ms**, respectively. No consistent penalty from merely retaining eleven quiet, hidden panes surfaced. This does not test eleven **visible** or streaming conversations, nor is it a claim that hidden panes improve scrolling. [Matched-size fullscreen scroll trains](qa/webkit-spa-responsiveness/pane-fullscreen-scroll.csv).

## Follow-up tests

Keeping the **visible** text and row geometry changed the diagnosis. Removing ordinary menu machinery or using warm pre-parsed paragraphs did not consistently recover the fast scroll control. Even completely inert clones of the real DOM still had long gaps. In contrast, retaining live components and flattening their visual decorations reduced the typical gap from 182.5 to 55 ms in a separately baselined GTK comparison. [Paired row measurements, exact controls and reproduction](qa/webkit-spa-responsiveness/row-entry-rendering.md).

On fullscreen exit the [first revealed feed's width read](qa/webkit-spa-responsiveness/pane-fullscreen-attribution.md) took 243 to 335 ms. Supplying the **correct** cached width moved that delay to the next scroll offset read. Preserving the post-commit check but removing a redundant pre-commit range publication is justified by the one-publication contract, not by latency: twelve-pane exit was 694.5 ms stock versus 696 ms with that change.

On the post-shadow build, [removing the custom scrollbar, CSS containment and batching the virtual range](qa/webkit-spa-responsiveness/feed-scroll-scheduling.md) did not produce a repeatable, behavior-preserving improvement. Removing the scrollbar looked substantially faster in the first series but came out slower on the typical-gap metric in the follow-up. Retaining hidden pane layout boxes and [caching titlebar measurements](qa/webkit-spa-responsiveness/pane-fullscreen-attribution.md#tab-measurements) likewise did not improve default 12-pane transitions in both directions.

The [upstream research](qa/webkit-spa-responsiveness/webkit-virtualization-references.md) found a GTK tile-damage fix and a separate Safari momentum/offset bug. Neither demonstrates what happened on this setup: the GTK report required a scrollbar fade, the Safari test interrupted momentum with a programmatic scroll, and our detector had already found exposed pixels during ordinary wheel input.

[Two output columns 1,004 px apart](qa/webkit-spa-responsiveness/scroll-row-paired-stripes.md) later showed the sizer at common vertical positions in **three of four** normal trains, up to 221 px in common. There were **zero intercepted JavaScript writes to the sampled viewport's scroll offset** during all six trains; the detector recognized a deliberate write before timing. No late-window sample showed the band. The custom scrollbar stayed visible, so this did not exercise the upstream fade. Two short `top`-positioned trains showed no band; that is too small a control to recommend replacing transforms, and the callback comparison above did not favor `top`.

**Tool disclosures are a separate cost.** A collapsed Bash/Read/Exec/Edit group mounted no member cards and ran no diff. On explicitly opening an Edit with one changed line in a 450-line file, the [diff builder](../web/src/lib/components/chat/tools/content/chat-tool-diff.ts) now initializes four matrix cells instead of 203,401. It retains the full-input rejection limits and old line-number choices, including duplicates. In the [paired Bun benchmark](../web/scripts/benchmark-chat-tool-diff.ts), head/middle/end edits took roughly 0.07 to 0.10 ms versus 1.7 to 2.5 ms; a change at both ends still needs the full matrix. This is CPU work per disclosure, not whole-page latency.

## What to optimize next

- **Keep real text and interactions.** Test individual visual changes against the live row's dimensions, content, controls and reading anchor. Repeat useful findings on code, tools, long messages and incoming output; a cheaper blank row is not success.
- **Reduce the work that dirties layout on fullscreen transitions.** Skipping a getter is not the same as avoiding that work. Keep immediate stale-view fencing, correct drafts, pinned ends and detached anchors.
- **Keep two scroll checks.** Use the uninstrumented wheel trains to track interactive latency and the independent output check to catch painted gaps. Neither can substitute for the other. A physical Linux GPU would test rasterization and presentation; a real iPhone would test touch momentum, the compact layout, keyboard and VoiceOver. Neither is necessary to reproduce the real-row cost in this report. The earlier [popup and stylesheet experiments](webkit-spa-responsiveness.md) cover separate bugs; there is no single proven cause of every slow action.

## Reproduce

Use production revision `cb649885f` and a private fixture with twelve synthetic direct chats. Seed 28 short paragraphs in each initial prompt, then add 48 variable-length echo turns to the active chat (98 entries). Use the same origin, data, preferences, fonts and balanced desktop layout throughout each comparison. The tall-feed matrix has one visible pane in an 1840 x 960 window. No provider turn is running during timing. GTK is MiniBrowser with Xvfb and no physical GPU; Chromium is headless shell. Browser sweeps, builds and traces did not run concurrently.

1. Build the [isolated diagnostic copy](qa/webkit-spa-responsiveness/scroll-mount-probe.md). The application does not ship its query flags. On a normal page walk the complete transcript at settled geometry and collect the 100 keyed sizes. For each new lightweight page, arm only after arriving at the first anchor. Reuse that engine's own sizes.
2. Install the [wheel probe](qa/webkit-spa-responsiveness/measure-wheel-train.js). Set the start item to -5 px relative to the viewport, wait for stable geometry, then call `armGarconWheelTrain(viewport)`. After `ready()`, send 14 native wheel actions of 120 px at a target cadence of 60 ms. Use distinct WebDriver wheel source IDs on GTK 2.50.6: a rejected preflight reusing one ID delivered only one event. For Chromium use Playwright mouse wheels.
3. Wait for `settled()`, then call `finish()`. Include both intervals crossing the input window, from the last callback before the first wheel through the first callback after the last wheel or scroll. The probe requires at least three further callbacks and 180 ms of idle time. Keep actual delivery timestamps; do not assume the driver met its schedule. Always call `cancel()` when abandoning an armed probe.
4. Use fresh documents in order normal, retained, lightweight, normal, lightweight, retained, normal. Discard the first down/up pair in each block; keep three further pairs on GTK and two on Chromium. Repeat with diagnostic counters separately. Validate the range, direction, delta, visible anchor and placeholder dimensions outside timing.
