# Why popups slow down with tiled chat panes on Linux

Reproduced on `e3e5e1faf` with **one OS window**, 1, 8, or 12 visible chat panes, and no running agents. Opening the pane's three-dot menu or Settings got slower in both packaged Garcon and standalone WebKitGTK. Chromium stayed substantially faster on the same page. The Tauri host is not necessary to reproduce the problem; the evidence points first to how the page styles and renders popups over a large workspace.

## Changes Tested In The Packaged App

The branch upgrades Bits UI to 2.22.0. Only [Settings](../web/src/lib/components/settings/Settings.svelte) opts out of the inherited body pointer lock: its existing full-viewport overlay handles pointer input, and Bits still locks scrolling and manages focus. Only the [pane's three-dot menu](../web/src/lib/components/workspace/WorkspaceWindowTabMenu.svelte) uses a transparent [pointer backdrop](../web/src/lib/components/ui/dropdown-menu/dropdown-menu-content.svelte) behind the portalled content instead of the body scroll lock. The workspace document already disallows scrolling. The menu keeps fixed positioning, its own scrollable list, and Bits' dismissal and keyboard handling. Other dropdowns, right-click menus and dialogs keep their defaults. No native changes or theme changes.

Fresh production builds, the same Linux `.deb` and WebKitGTK 2.50.6, three completed turns per chat, same 1840 x 960 viewport. Medians in ms, seven warm opens per popup. The middle column isolates the prop and backdrop changes from the dependency upgrade. Compare **within this matrix**; absolute software-rendered timings vary across runs.

| Open popup | Original 2.19.5 | 2.22.0 defaults | 2.22.0 with backdrops |
| --- | ---: | ---: | ---: |
| Pane menu, 1 / 8 / 12 panes | 152 / 430 / 595 | 157 / 431 / 690 | 134 / 319 / 452 |
| Settings, 1 / 8 / 12 panes | 331 / 587 / 696 | 302 / 568 / 768 | 300 / 456 / 554 |

At twelve panes, the protected menu was 35% faster than the upgraded default and 24% faster than the original build in this run. Settings was 28% and 20% faster, respectively, **with the theme's blur still on**. One-pane Settings barely changed versus the upgraded default. Neither change makes WebKit behave like Chromium. In particular, the median time just to observe the popup DOM remained about 250 ms at twelve panes. The main win comes *after* that point.

- **Do not ship the bare menu opt-out.** With just `preventScroll={false}` and `strategy="fixed"`, the 12-pane menu took 435 ms, but a real WebDriver click on a second pane's menu button dismissed the first **and opened the second**. With the transparent backdrop (452 ms) that click hit the backdrop and only dismissed. In the packaged app, arrow keys focused a menu item, Escape restored the trigger, and a wheel scrolled the menu but not the covered chat. The same wheel input scrolled the chat after dismissal. The [browser regression](../integration-tests/tests/chromium/workspace-popup-interaction.test.ts) also checks that a touch tap dismisses without hitting the pane behind it; this is touch emulation, not an iOS-device result.
- **Keep the dialog overlay even when it is visually transparent.** Settings with its opt-out kept the body at `pointer-events: auto`, with inline `overflow: hidden`. Clicking at a pane button hit the overlay, never the button. Opening the nested typography dialog independently set body pointer-events to `none`; closing it restored `auto` without losing the outer scroll lock. Tab stayed inside Settings. Pointer hit testing does not itself trap keyboard focus or remove the background from the accessibility tree. Elements painted above an overlay still need a stacking review; the notification cards, for example, already explicitly request `pointer-events: auto`.
- **Other options tested separately.** Keeping dimming but removing only the blur took 483 ms versus 554 ms for the optimized 12-pane Settings. With blur on and both pointer backdrops in place, an interleaved run gave 400 / 547 ms (menu / Settings) with normal styling, 428 / 563 with `contain: layout paint` on each tile, and 419 / 557 with only popup entrance animations disabled. All retained 96 transcript rows. Neither containment nor removing entrance animations demonstrated a win; neither is on the branch. This measures two frames, not the time for an entrance animation to finish.

[Raw follow-up samples](qa/linux-webkit-pane-popups/popup-options.csv) include warm-up sample zero. The three builds used the same reducer-seeded fixture and input probe, rotating popup order; the CSS experiments alternated variants in the same loaded page. Coordinates for the outside-click checks came from the underlying button, not a synthetic event dispatched directly on it.

## Original Measurements

Median milliseconds from dispatching input to the second animation frame after the open popup appeared in the DOM. Seven warm opens per cell; not a measurement of display scanout or total time from a physical click.

| Linux client | Menu: 1 pane | 8 panes | 12 panes | Settings: 1 pane | 8 panes | 12 panes |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Garcon 0.4.2, packaged .deb | 297 | 471 | 725 | 639 | 833 | 1,063 |
| Garcon 0.4.2, AppImage payload | 275 | 512 | 661 | 672 | 797 | 904 |
| Standalone WebKitGTK MiniBrowser | 438 | 633 | 770 | 984 | 1,053 | 1,305 |
| Chromium 156 | 58 | 123 | 112 | 67 | 111 | 107 |

There is work both before and after the popup mounts. At 12 panes the .deb took a median **309 ms** just to observe the menu DOM and **298 ms** for Settings. Chromium took **27 ms** and **49 ms** respectively. This is not just a cold Settings import, nor does it isolate JavaScriptCore versus V8: style resolution, layout, and frame scheduling also occur on this path.

An independent X11 input spot check on the .deb also reproduced it: two trusted mouse clicks opened the 12-pane menu in 710 and 629 ms, and a trusted `Ctrl+,` opened Settings in 903 ms, timed from the input event inside the page. A later keyboard event opened Settings but was not captured by the timing probe. These spot checks are not included in the medians.

## Original Findings

- **A local menu changes input styling across the document.** Garcon's [dropdown wrapper](../web/src/lib/components/ui/dropdown-menu/dropdown-menu-content.svelte) uses Bits UI's [default scroll lock](https://github.com/huntabyte/bits-ui/blob/fd10616a873a8e6e3652e31dcc88c5c2f155a9e2/packages/bits-ui/src/lib/bits/utilities/popper-layer/popper-layer-inner.svelte). The [lock](https://github.com/huntabyte/bits-ui/blob/fd10616a873a8e6e3652e31dcc88c5c2f155a9e2/packages/bits-ui/src/lib/internal/body-scroll-lock.svelte.ts) sets `pointer-events: none` on `body`. This property is inherited; the page already has `overflow: hidden`. In a paired 12-pane test on the .deb, keeping the computed body pointer-events at `auto` during open reduced median menu time from **702 to 421 ms**. The menu still had the same 163 descendants; the same 96 transcript rows stayed mounted. Merely making the other 11 panes invisible without changing their layout gave **668 ms**. This implicates the document-wide change, not just drawing the pixels behind the menu. The pointer-events override was a diagnostic, not a safe fix for modal interaction.
- **Dialogs pay separately for full-viewport blur.** [The dialog overlay](../web/src/lib/components/ui/dialog/dialog-overlay.svelte) covers the viewport. The [shared style](../web/src/app.css) applies a backdrop filter, measured at `blur(4px)` with the default theme. In the same controlled run, removing **only the filter**, keeping the dim color, pane geometry, and 347 Settings descendants identical, reduced Settings from **1,001 to 680 ms**. Time to observe the DOM was essentially unchanged (300 versus 306 ms). The chat menu has **no** such backdrop. In the main comparison, using the existing preference to turn off both dimming and blur reduced 12-pane .deb Settings from **1,063 to 718 ms**.
- **Pane and menu content multiply the exposure.** [WorkspaceRoot](../web/src/lib/components/workspace/WorkspaceRoot.svelte) renders each visible tile; [WorkspaceWindow](../web/src/lib/components/workspace/WorkspaceWindow.svelte) mounts its active conversation. Transcript virtualization limits rows *per pane*, not per workspace. The .deb went from about 770 DOM elements and 8 mounted transcript rows at one pane to about 3,050 and 96 at twelve. The [menu](../web/src/lib/components/workspace/WorkspaceWindowTabMenu.svelte) also builds a move destination for every other window on open: the measured popup grew from 108 descendants to 163. Warm menu opens made about 29 bounding-rect and 107 computed-style calls at one pane versus 42 and 154 at twelve. These counts identify follow-up targets; they do not imply every call forced a layout. Settings mounted a constant 347 descendants yet also slowed down, so the menu's extra items cannot explain the common problem.

## Upstream Findings

As of November 23, 2026, no open Bits UI issue matched this popup slowdown. [Open #1955](https://github.com/huntabyte/bits-ui/issues/1955) concerns accidental selection on right-button release, not rendering latency. [Closed #2258](https://github.com/huntabyte/bits-ui/issues/2258) reports the same inherited body style change: 3,294 elements restyled in 41 to 63 ms in Chrome, versus two elements in 0.2 ms for the overflow lock alone. [Merged PR #2282](https://github.com/huntabyte/bits-ui/pull/2282) separately measured one toggle at 38 ms in WebKit versus 9 ms in Chromium on 30,000 synthetic nodes. These are style-change measurements, not the Garcon popup timings above.

Bits UI writes the inline style, not Garcon's shadcn-style wrapper. With `pointer-events: none` on the body, descendants that inherit it are skipped when the browser chooses a mouse or touch target. The popup content explicitly sets `auto` so it remains interactive. Restoring the body value on close changes inheritance again. This is different from locking scrolling, trapping Tab, or hiding background content from assistive technology; removing the body style is only safe here because another element intercepts the outside pointer.

[Bits UI 2.21.0](https://github.com/huntabyte/bits-ui/releases/tag/bits-ui%402.21.0) added `preventBodyPointerEvents={false}` to Dialog and AlertDialog content. With a mounted overlay, it can block outside clicks without changing body pointer-events or giving up the scroll lock. Without an overlay it falls back to body blocking. The original Garcon revision pinned 2.19.5. The new prop defaults to true and does not apply to DropdownMenu. The upgrade also brings upstream's [focus-scope](https://github.com/huntabyte/bits-ui/pull/2264) and [ScrollArea teardown](https://github.com/huntabyte/bits-ui/pull/2261) fixes, replacing Garcon's old dependency patch.

## Native Boundary

[The Rust host](../native/src-tauri/src/host.rs) creates a WebView for a server window, not for a workspace pane or an in-page popup. Menus and dialogs are DOM portals. The [root layout](../web/src/routes/+layout.svelte) owns the primary chat WebSocket; adding chat tiles does not start a new connection per tile. The slowdown persists with no transcript traffic, so neither streaming, a reconnect storm, nor opening another native window is required. The [earlier split-chat investigation](desktop-split-chat-performance.md) measured a different workload: the cost of appending to long, actively streaming transcripts.

The .deb loads the system WebKitGTK (2.50.6 here). The AppImage from the same [CI build](https://github.com/cfal/garcon/actions/runs/45115528428) includes its own WebKitGTK and JavaScriptCore (2.50.4). Both reproduced it. Updating the system engine alone is not the same experiment for the two packages.

## WebKit Patterns And Next Probe

**Check the actual renderer.** Open `webkit://gpu` in a matching Linux MiniBrowser. Record the WebKitGTK version, display backend, scale, buffer type and `GL_RENDERER`, not just the hardware acceleration policy. In this VM the [diagnostic page](https://github.com/WebKit/WebKit/blob/webkitgtk-2.50.6/Source/WebKit/UIProcess/API/glib/WebKitProtocolHandler.cpp#L478-L550) reported X11, scale 1, 60 Hz timer vblank, policy `always`, shared-memory buffers and Mesa `llvmpipe`: an accelerated API backed by a software renderer. A system browser does not identify the AppImage's driver or libraries. Don't force compositing flags based on these numbers.

**Separate layout from painting on the reporter's desktop.** Record one warm open at 1 and 12 panes in an undocked [Web Inspector Layout & Rendering timeline](https://webkit.org/web-inspector/timelines-tab/#layout-rendering-timeline) with screenshots off. Look for synchronous layout and its JS call stack before popup insertion; inspect paint/composite work and full-viewport layer size afterward in [Layers](https://webkit.org/web-inspector/layers-tab/). Measure input-to-frame separately with Inspector closed. WebKitGTK 2.50.6's [PerformanceObserver entry types](https://github.com/WebKit/WebKit/blob/webkitgtk-2.50.6/Source/WebCore/page/PerformanceObserver.cpp#L151-L165) do not include Chromium's `longtask`, `long-animation-frame` or `event`; an empty collection does not rule out a stall.

For a timing on your own desktop, start with all popups closed. Run the [one-open probe](qa/linux-webkit-pane-popups/measure-next-open.js) in the Web Inspector console of the same Garcon page, close Inspector, and click a pane's three-dot button or press `Ctrl+,`. Reopen Inspector and evaluate `performance.getEntriesByType('measure').filter(e => e.name.startsWith('garcon:')).map(e => [e.name, Math.round(e.duration)])`. Re-arm the probe for each sample. It measures from the captured input event to DOM observation and to the second subsequent frame callback; it doesn't read chat content, time OS input delivery, or establish when a frame reached the screen. Use a matching MiniBrowser if the release shell doesn't expose Inspector.

**Measure before changing floating behavior.** [Bits' floating layer](https://github.com/huntabyte/bits-ui/blob/8278045215dc4e847068559e629ab79f7ad9a8c9/packages/bits-ui/src/lib/bits/utilities/floating-layer/use-floating-layer.svelte.ts#L263-L267) runs Floating UI's `autoUpdate` while anchor and menu are mounted, not a perpetual animation-frame loop by default. In the optimized `.deb`, the menu went from a median 23 bounding-rect and 89 computed-style calls at one pane to 36 and 136 at twelve. None of the four warm opens at either size reread the [tab strip's measurement items](../web/src/lib/components/workspace/WorkspaceWindowTabStrip.svelte). Call counts are not forced-layout counts. Next: compare normal positioning to [ContentStatic](https://bits-ui.com/docs/components/dropdown-menu#contentstatic) at the same measured anchor, holding menu items, focus and input blocking fixed. Static positioning is not a production replacement for collision handling, zoom and scrolling.

**Do not replace the focus trap to save a layout read.** [FocusScope](https://github.com/huntabyte/bits-ui/blob/8278045215dc4e847068559e629ab79f7ad9a8c9/packages/bits-ui/src/lib/bits/utilities/focus-scope/focus-scope.svelte.ts#L95-L126) schedules autofocus; [tabbable](https://github.com/focus-trap/tabbable/blob/v6.5.2/src/index.js#L383-L448) checks computed visibility and `getClientRects()`. Settings made 42 of each inside the dialog at both one and twelve panes. A separate alternating 12-pane diagnostic explicitly focused the same search input with `preventScroll: true` on the opening frame. It removed all 42 client-rect calls, but did not improve time to two frames (865 ms default, 907 ms explicit; seven warm samples per case, variable shared-VM load). This is fixed dialog work, not evidence for pane-count scaling. No autofocus override was kept. [Geometry and focus samples](qa/linux-webkit-pane-popups/geometry-probes.csv) are separate from the main timing runs.

**Do not treat covered panes as offscreen.** [CSS containment](https://www.w3.org/TR/css-contain-2/#relevant-to-the-user) treats on-screen, focused and selected content as relevant. A popup over 12 visible panes doesn't turn 11 of them into offscreen content. Style containment does not stop inheritance; layout/paint containment can change positioning or clip content. [The existing virtual-list driver](../web/src/lib/virt/virtual-list-dom-driver.ts) already consumes observed row sizes. The containment and animation A/Bs above give no reason to remount panes, add global `will-change`, or drop focus/selection state.

## Reproduction

- Build the production web app with `bun run build`. The native package serves only the launcher; connect each client to the same server-hosted UI revision.
- Run `bun test integration-tests/tests/chromium/workspace-popup-interaction.test.ts` to verify hit testing, scrolling, focus return and nested locks. The test checks behavior, not VM-dependent timing thresholds.
- Use an isolated controller with 12 chats, three completed fake-provider turns each, Markdown paragraphs and lists, no active turns, and an open sidebar. The [split-chat fixture](../integration-tests/tests/chromium/split-chat-endurance.test.ts) demonstrates seeding `workspace_layout_v2` using the real workspace reducer. Keep all 12 chats in the sidebar while changing only the number tiled.
- At a fixed 1840 x 960 CSS-pixel viewport, open the same pane's three-dot menu and open Settings with `Ctrl+,`. Close between trials. Discard the first open of each kind and alternate test order. For the user-facing workaround compare **Settings > Appearance > Dim and blur behind overlays** on and off.
- For the measurements, a capture in the page observed the open popup's DOM insertion and two subsequent animation-frame callbacks; driver/network round-trip times were excluded. The controlled tests used six warm samples per variant, verified computed styles, and kept all 96 rows mounted. The idle 12-pane .deb frame interval was about 16 ms. [Individual samples](qa/linux-webkit-pane-popups/popup-samples.csv) include the discarded first opens.
- Linux X11 under Xvfb, shared VM, no GPU device passed through. This reproduces the engine difference without measuring the reporter's display stack, Brave build, GPU acceleration, or absolute laptop latency. File, terminal, and streaming workloads were not measured.
